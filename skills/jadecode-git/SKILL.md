# JadeCode Git Workflow

本技能包含执行 Git 工作所需的完整边界，不依赖仓库之外或可能被忽略的说明文件。
始终以当前仓库状态和用户最新指示为准。

## 判断当前模式

- 用户要求“看看怎么提交”或“给提交方案”：只做规划，不暂存、不提交。
- 用户批准了明确方案：只执行获批的批次和文件。
- 用户要求 push：先核对 remote、branch 和待推送提交；commit 授权本身不包含 push。
- 用户没有提出 Git 操作：不要主动提交。

commit、push、amend、reset、rebase、force push 和删除文件分别授权，不能互相推导。

## 提交前置条件

提交前确认实现已经 Review、没有已知阻塞问题、要求的自动测试已经通过，并且需要真机验收的功能
已经由用户验收。清理自行创建的临时文件，识别范围外修改；不得提交空骨架、半成品、失败测试、
构建产物、密钥或归属不明的文件。

## 规划

规划前读取：

- 当前 branch、status 和 upstream；
- tracked diff、untracked 文件内容及已有 staged diff；
- 近期提交历史；
- 自动测试和真机验收状态。

按依赖关系设计最小完整提交，而不是机械地一文件一提交。
每个提交应语义完整、可以独立理解和回滚，并且不依赖尚未提交的后续文件才能编译。

每批说明：

- 单一目标；
- 精确文件；
- 前置依赖；
- 验证要求；
- commit message；
- 明确保留的范围外文件。

方案必须先交给用户审批。审批后如果 diff 或文件集合发生实质变化，停止并重新确认。
已有 staged 内容不得直接覆盖或混入新计划，先报告其来源并等待决定。

## 执行

只使用精确路径暂存。禁止 `git add .`、`-A`、`--all` 和通配暂存。

每批提交前检查：

- `git diff --cached --name-status`；
- `git diff --cached --stat`；
- `git diff --cached --check`；
- staged 完整 diff；
- whitespace/conflict 错误；
- 敏感信息、构建产物和范围外文件。

确认 staged 内容与批准方案完全一致后才 commit。完成一批并记录 hash 后，再执行下一批。

全部完成后检查 log、status、upstream 领先状态和残留文件。

完整工作区测试通过不自动证明中间提交可独立构建，因为未提交源码仍可能参与编译。
复杂拆分若无法通过依赖分析确认，应在获得相应授权后使用隔离的临时 worktree 验证。

## 安全边界

未经单独明确授权，不执行：

- push；
- amend；
- reset；
- rebase；
- force push；
- 删除或忽略 stray 文件；
- 任何可能覆盖用户未提交工作的操作。

发现工作区漂移、已有 staged 内容、归属不明修改、测试失败或敏感信息时，停止 Git 写操作并报告。

默认保留已推送历史；修复已推送问题优先使用新提交。
暂存错误只撤销对应路径的 staged 状态，不覆盖工作区。任何历史修正都先提出方案并保护用户未提交改动。

## 提交质量

提交必须原子、语义完整并可独立构建。不提交空骨架、半成品、失败测试、临时文件或秘密。

标题使用不超过 72 字符的祈使句，描述实际能力或行为；不加句号，不写 AI 署名。正文只解释 diff 看不出的原因或约束。

正文不逐文件复述 diff，不记录失败的中间版本，也不写“测试通过”之类流水账。

最终报告列出 commit hash、标题、验证、branch/upstream 状态、残留文件以及是否 push。
