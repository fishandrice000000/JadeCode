## 1. 本轮设计解决什么问题

仅有提取服务，真实 CLI 不会自动保存；仅有召回服务，下一次任务也看不到它的返回结果。
因此要把记忆放在两个明确的生命周期边界：

```text
用户开始任务 → 召回一次 → 主任务请求 / 工具 / Stop 续跑 → 真正完成
                                                        ↓
                                            提取新增 → 数量触发整理
下一次任务 ← 从工作区 .memory 重新读取
```

“每次任务”指一次 AgentLoop.run，不是 while 的一次迭代。Stop 注入的文本仍属于当前任务，
不是一个新的用户意图；辅助模型的 JSON 也不是主任务回复，不能送进工具分发或再次触发 Stop。
主任务失败时不提取，记忆维护失败则明确报告，不把已完成主任务倒算成失败。

原课程提供这两个时机、十条数量触发、同客户端辅助调用与整库候选。
JadeCode 增加了完整输入预算、整批结构拒绝、坏文件保护、候选先落盘及普通失败恢复。
这些保障不等于模型语义必然正确、全库事务或并发隔离。

## 2. 精简阅读顺序

1. [AgentLoop.run](../../../src/main/java/com/jadecode/agent/AgentLoop.java)：只看 taskSystem 的生成与
   Stop 允许结束后的 finishTask。先定位“谁决定任务开始 / 结束”，不用重读 s08 全部细节。
2. [MemoryManager](../../../src/main/java/com/jadecode/memory/MemoryManager.java)：看 prepareSystem 如何
   把背景限定在本次任务，finishTask 如何区分主任务成功、候选生成成功与实际新增成功。
3. [MemoryConsolidationService.consolidate](../../../src/main/java/com/jadecode/memory/MemoryConsolidationService.java)：
   看数量触发 → 完整库输入 → 专用无工具模型 → 整份候选校验 → 发布。
   整理是模型重写多份知识记录，不只是调用一个“合并文件”的字符串函数。
4. [MemoryStore.replaceRecords](../../../src/main/java/com/jadecode/memory/MemoryStore.java)：按需看
   为什么整库输出不能像提取一样部分接受、为什么先准备候选，以及普通失败怎样保留原知识。
5. [Main.buildLoop](../../../src/main/java/com/jadecode/Main.java)：最后确认父循环启用、子代理未自动读写；
   既有 [装配测试](../../../src/test/java/com/jadecode/MainCompactionAssemblyTest.java) 只调整辅助请求分类。

## 4. 最小真机验收（由用户决定何时执行）

建议在专用临时工作区运行绝对路径 JadeCode 脚本，避免实验记忆污染日常项目。
先确认该目录与脚本路径；不要把密钥写到输入或笔记，现有配置由用户自行提供。

1. 开始一个任务，明确提出一个无秘密的长期偏好（例如“以后解释 Agent 架构时先讲需求，再讲数据流，请记住”）。
   观察完成后的 [Memory] 诊断，检查实际新增文件与 MEMORY.md，不只相信模型说“记住了”。
2. 退出并重新启动 CLI，用新历史询问这个偏好；检查能否召回，而不是复用上一进程消息。
3. 再提出一次性限制，确认它没有被写成长期规则。若误保存，记录原对话与候选文件，属于模型分类问题，
   不把单次成功或失败归纳成永久语义保证。

小库无需为了验收凑够十条；整理的机械主路径已有离线证据，真实合并质量可在以后自然触发时观察。
