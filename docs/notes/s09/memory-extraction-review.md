## 1. 需求与设计意图

M1 能把已有知识带到新请求里，但这些知识还需要有人生成。
M2 让任务结束时的对话成为知识候选来源，不要求用户逐条手写 Markdown。
例如“以后 Java 要有详细中文注释”可能值得跨会话保存，而“这次只读”通常只约束当前任务。

语义价值交给模型判断；程序不使用临时词匹配替模型做决定。
但是“模型认为值得保存”与“文件已成功保存”不是一回事：字段、scope、路径和写入都仍有明确契约。
本轮选择只新增、不覆盖，以保护已有知识；同时承认这不能独自解决纠正、矛盾与语义重复。

## 2. 推荐阅读顺序

1. [MemoryExtractionService.extract](../../../src/main/java/com/jadecode/memory/MemoryExtractionService.java)：
   先从一次任务结束后的输入 / 输出看主流程：准备数据 → 模型候选 → scope / 结构检查 → 保存 → 结果。
   不先逐项背异常与字段，先确认哪一步开始有磁盘副作用。
2. 同文件的 EXTRACTION_SYSTEM、dialogueText、Status / ExtractionResult：
   看模型被要求判断什么、它实际能看到哪些信息，以及失败与成功零新增为何不能混为一谈。
3. [MemoryStore.saveNew](../../../src/main/java/com/jadecode/memory/MemoryStore.java)：
   看新知识怎样成为独立文件，为什么不覆盖旧记忆，为什么实际新增数不能使用模型建议数代替。
4. 再按需看 MemoryDraft、memoryDocument 与索引发布：
   这些是结构、格式和存储保障，不是另一个长期价值判断模型。文件名正则只是路径组织，不是临时词否决。

## 3. 主循环与辅助提取的边界

本服务只提供 extract(messages)。什么时候任务“真正结束”，仍由主循环判断：
主模型不再调用工具，且 Stop hook 不要求续跑之后，才是未来合适的接入点。
构造服务、调用一次工具、模型暂时输出一句结束语，都不等于应当立即自动写记忆。

辅助提取不带工具，不执行回复中的指令，不调用 Stop，也不改写原 messages。
它的失败状态属于记忆维护；不能仅凭这个状态推断刚才的主任务也失败了。
最终接线仍要明确如何报告辅助失败，特别是用户明确要求“请记住”时，不应假装已经保存。

## 4. 你选择的语义策略如何体现在代码里

- 模型给 scope=current_task 的条目不保存；只有 persistent 进入新增草稿。
- 程序检查字段与类型，不用“本次、当前、暂时”等词搜索正文。
- 因此即使正文含“暂时”，模型若误标为 persistent，程序仍可能保存。去掉粗糙过滤并不意味着误判消失。
- 当前输入保留最近消息中的纯文本，不包含工具块正文；但助手推测、被压缩的摘要和 hook 的 synthetic user
  仍可能出现在纯文本里。角色与 prompt 只能帮助判断，不提供完整来源证明。
- 已有目录用于让模型避免明显重复，程序的文件名碰撞防护则防止覆盖；两者不等于可靠的语义去重。

## 5. 为什么文件与索引分开

记录文件保存正文，MEMORY.md 是可由合法记录重建的导航。
程序先写本批新记录，再产生完整新索引，临时索引关闭后一次替换正式索引。
M1 读取会直接扫描记录文件，不只依赖这个索引，所以不能把索引与实际库状态当成同一份东西。

普通写入失败时清理本批新记录，不删除旧知识；清理失败会随原异常报告。
但是程序崩溃可能来不及清理，而且多份记录不是一次原子发布，不能称为完整数据库事务。
本轮没有为了这一步引入恢复日志、锁、自动清理或并发协调服务。
