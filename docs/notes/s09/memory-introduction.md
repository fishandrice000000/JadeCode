## 1. 从一个新会话开始

昨天你告诉 Agent：“我希望生成的代码有详细中文注释。”今天关闭程序后重新打开，要求它实现一个工具。
新 messages 没有昨天的话，模型就没有这条背景；模型本身不会因为昨天聊过就自动更新权重。

Memory 的办法是：昨天把适合长期使用的偏好保存成外部记录；今天由 harness 找到相关记录，
把它加入模型本次收到的上下文。所谓“记住”，最终仍落实为“下一次请求能看见这条信息”。
文件存在只是存储完成；没有相关选择与注入，模型仍不知道它。

## 2. 为什么不是直接复用 transcript

transcript 回答：“当时具体发生过什么？”Memory 回答：“下次遇到相关任务，哪些知识仍值得参考？”

例如同一次排查里可能出现三种内容：

- “以后生成的 Java 都要详细中文注释”：可能是跨会话工作偏好。
- “这次只读，不修改任何文件”：本轮限制，不应永久限制以后的编码任务。
- “终端输出了一千行日志”：历史证据，可归档，不应整份变成长驻记忆。

把旧日志全发回去会重新占用上下文，还可能带入过期状态与临时命令。
因此 s09 不是“s08 再做一次摘要”，而是选择知识的用途、有效范围和召回时机。

## 3. 本章四个机制各自解决什么

**存储**：知识离开内存后仍存在。课程用 `.memory/*.md` 保存正文，用 MEMORY.md 保存简短索引。
索引让选择者先了解“有哪些知识”，而不用把所有正文先发送给模型。

**召回**：当前任务只需要其中一部分。请求实现 Java 工具时，注释偏好可能相关；
某次餐饮偏好通常无关。先选相关条目，再有界加载正文，既控制成本，也减少无关知识干扰。
它与 s07 都使用目录与正文分离，但课程 s09 是 harness 的辅助请求选择记忆，不是复制 load_skill 工具。

**提取**：用户不必每次都说“请记住”。主任务结束后，辅助模型给出值得保存的候选；
harness 再检查格式、scope、临时含义与重复。模型建议保存不等于可直接写盘。
Stop 若要求继续工作，任务尚未真正结束，不应每次暂时停止就当成最终结束。

**整理**：长期记录可能重复或过时。“偏好 tab”以后被“改为四空格”纠正，
不能让矛盾条目无限累积。整理是维护知识，不是缩短当前工具交换；失败也不能假装替换成功。

这四件事分开后，可以先学会“给定已有知识如何服务新请求”，再学习自动写入与维护。
不需要先实现全部底层工具，最后才看到 Memory 在 Agent 中的作用。

## 4. 记忆不是更高权限的命令

旧记录可能写着“通常使用 tab”，当前用户却明确要求“本文件使用空格”。
召回的旧偏好不应该替当前用户做决定；它提供默认背景，不拥有永久否决新请求的权限。

这也解释了为什么提取时要区分 persistent 与 current_task：
否则昨天的“不要修改文件”会悄悄影响今天的实现任务，系统就不再忠实于当前目标。
声明 scope、关键词过滤与提示分区都只是降低风险，不保证模型永远不会误判或旧知识永远不过期。

假设 `.memory` 已保存“Java 代码需要详细中文注释”，新会话却生成了几乎没有注释的代码。

**01 从 Agent 数据流看，存储之后还缺哪些环节？为什么仅证明文件存在还不足以证明记忆能力有效？**

只有持久化, 并不意味着记忆会被模型读取. 因此需要有召回机制来判断什么时候需要将记忆内容加入到上下文中.

### M02：有用的过去为何也可能伤害当前任务

昨天你说“这次只做调查，不修改文件”，今天让 Agent 实现一个功能。
如果昨天的话被当成长期记忆并召回，Agent 可能发生什么目标偏移？
你希望提取阶段与召回阶段分别承担怎样的职责，而不是把问题全交给主模型自行猜测？

回答：

**01 如果昨天的话被当成长期记忆并召回，Agent 可能发生什么目标偏移？**

Agent 可能会因已过期的内容而不好好完成当前的任务. 而且出现这种情况可能会降低模型在当前任务下的表现.

**02 你希望提取阶段与召回阶段分别承担怎样的职责，而不是把问题全交给主模型自行猜测？**

提取阶段的职责就是负责把用户的提示词做成记忆呀; 召回阶段的职责就是负责把用户的记忆在合适的时候注入到上下文中呀. 这有什么可问的?
