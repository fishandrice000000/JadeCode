# JadeCode 优化候选清单

建立日期：2026-10-13。
用途：记录学习与实际使用中遇到的问题、优化动机、候选方案和待确认条件，避免只记方案而忘记为什么需要它。
本文件不是用户答题笔记，也不是立即执行的开发任务；不替代各章 jobs。
各条目的实施状态分别记录。后续选定候选项时再明确范围、契约、验证与提交方案，不为清空本清单扩大章节任务。

## OPT-001：减少未修改文件的重复读取输出

### 问题来源与动机

用户观察到 Coding Agent 会反复读取一些文件，并提出：若文件没有变化，重复返回整份正文可能让有效上下文
包含多份相同内容，增加输入 token 成本、挤占其它任务信息。希望减少这种重复，而不是让 Agent 放弃读取最新状态。

对 Codex CLI 的讨论建立在“每次读取都直接把结果再次放入上下文”的假设上；其实际内部行为尚未核实，
本清单不把该假设记录为已确认的 Codex 实现事实。

### JadeCode 当前事实

- ReadFileTool 每次执行都会读取文件并返回文本，没有按文件版本或会话上下文进行读取输出去重。
- 压缩可能把过去的正文替换为路径 / 预览或摘要；“以前读过”不保证原文仍在模型下一次请求的有效上下文里。
- 父子历史独立，父已经读过不能作为对子省略正文的充分理由。

### 优化目标与候选方案

在“同一 Agent 当前有效上下文仍含对应完整结果、文件内容与读取范围未变”的前提下，
考虑返回简短确认，例如用户提出的：

```text
File not modified. Check it in current history.
```

如果旧正文已不在有效上下文中，应正常返回正文或提供确实可用的恢复引用，不能只让模型寻找已经消失的历史。
这是读取输出 / 上下文去重，不等于工具结果的磁盘正文去重。

### 待确认条件与验收方向

- 用哪个逻辑会话标识记录可见性；压缩、摘要、历史替换和新子任务如何使记录失效。
- 比较实际解析后的路径、内容版本、读取参数与范围，不能只按文件名判断；仅依赖修改时间是否足够需核实。
- 保留强制重读能力，验证权限与路径边界不因缓存命中而绕过。
- 验证未修改 / 已修改、不同读取范围、压缩后原文不再可见、父子不同历史等场景。
- 对照模型实际收到的消息测量 token / 上下文收益，不仅证明缓存表命中。

状态：**候选，未实施**。相关历史讨论见 s08 总任务单的 READ-DEDUP 记录。

## OPT-002：按工作区与逻辑会话组织归档及调用记录

### 问题来源与动机

用户在讨论父子 Agent 共享压缩器时担心：归档与工具结果共用目录，会不会让父子转存内容覆盖或难以区分？
提出类似 `<workspace>/.transcripts/<session-id>/...` 的粗略目录设想；路径名称并未最终确定。

### 当前事实与问题澄清

- 当前 Main 为父子注入同一压缩器和目录：`.transcripts`、`.task_outputs/tool-results`。
- TranscriptStore 与 ToolOutputStore 每次创建新的落盘文件时使用 createTempFile，不按固定工具 ID 覆盖文件。
  同 ID、同正文再次保存也会得到独立文件；当前没有发现“父子转存互相覆盖”的 Bug。
- 同目录不等于把父子消息拼成同一份历史；现有问题主要是目录层面缺乏明确的会话归属、父子关系与回查索引。

### 优化目标与候选方案

保留用户“防止父子结果覆盖”的数据保护诉求，同时以实际缺口为目标：
让归档、调用记录明确属于某个会话 / 子委派，便于回查、恢复、诊断与后续生命周期管理。
不把目录重组误记为修复当前已经发生的覆盖故障。

使用显式逻辑身份，而不是 Java 执行线程 ID；父 REPL 会话跨轮保持 sessionId，子委派用独立 agentId
标识执行上下文并记录父子关系，不必把每次子委派都当成新的顶层会话。
资源根由明确的工作区决定，而不是随某条工具命令的临时 pwd 改变。

对话归档与调用记录可以按会话组织，工具结果正文是否也逐会话存储仍待决定。
另一候选是工作区共享正文存储，各会话保留独立记录并引用正文；这与会话归属隔离不冲突。

### 待确认条件与验收方向

- 会话的创建、结束、重启 / 恢复与子委派关系；不能将每次 REPL 输入都误当成全新的父会话。
- 决定分组哪些文件、保留哪些关联信息；目录层次本身不是权限隔离机制。
- 不改变既有不覆盖写入、完整归档、可信路径检查与摘要恢复引用契约。
- 路径重组后，旧引用如何继续有效；父子与不同工作区的恢复文件是否归属正确。
- 若正文共享，清理一个会话不得删除其它仍存活记录引用的内容；本条不授权执行任何清理。

状态：**候选，未实施**。目录与会话元数据方案尚未裁决。

2026-10-13 路径设计建议见 [会话归档与工具结果转存路径设计](session-storage-path-design.md)：
沿用工作区 `.transcripts` / `.task_outputs` 两个根，按 sessionId / agentId 组织；区分压缩快照与未来持续日志。
当前推荐逐 Agent 保存工具正文，继续排他创建、不覆盖；OPT-003 的共享正文方案暂不采用，也没有开始实施。

## OPT-003：不可变工具输出快照的存储去重与引用（讨论候选）

### 问题来源与动机

父子 Agent 在相同工作区可能得到完全相同的工具输出。当前新输出只要再次进入 saveOutput，
就会创建另一份文件；可能存在磁盘冗余。讨论能否在保留各自执行记录的同时，共享相同正文。

### 当前事实

当前只会在结果已经带有可信落盘 marker 时复用已有路径；没有对新工具调用的相同输出按内容去重。
“都读 example.md”不保证输出相同：文件版本或读取参数可能不同。
同样的命令也可能得到不同结果或产生副作用，不能因调用形状相同而跳过执行。

### 候选方案的概念

先取得本次实际输出，按正文内容识别一个输出对象；例如以 UTF-8 输出字节的 SHA-256 作为对象标识。
相同正文可引用同一对象，不同正文生成不同对象。哈希是索引，不替代完整性校验与可靠写入契约。

各会话仍有自己的调用记录，包含会话 / 调用身份、工具与参数、必要的来源 / 版本信息，以及 outputRef。
共享的是结果正文，不是调用记录、模型历史或工具执行次数。

不可变表示“已发布的输出对象不再更新；新输出创建新对象”，不是原始 example.md 永远不修改，
也不是普通文件天然不可写。外部篡改如何被发现属于待设计的完整性要求。

### 待确认条件与验收方向

- 在共享范围、访问权限和保留策略允许时才去重，不能仅凭同 hash 宣称跨项目 / 跨用户共享安全。
- 对象发布成功后才记录引用；处理写入失败、部分文件、已存在对象与内容校验，不返回不存在的恢复路径。
- 文件改变时旧快照仍可回查；不能覆盖共享文件，让所有旧引用悄悄读到新正文。
- 清理策略须保护仍被引用的对象，不能删除任一会话尚需的恢复证据。
- 衡量存储去重成本和收益；共享磁盘正文不自动减少模型上下文中的重复文本。

状态：**讨论候选，未确认采用、未实施**。当前仅记录设想，不引入内容寻址存储或新的缓存系统。

## OPT-004：结合流式传输完善响应块处理

### 问题来源与动机

2026-10-14 用户的 s08 真机日志多次出现“跳过未知响应块: ContentBlock”，但读取、父子压缩与继续回答的主路径正常。
用户推测这是未处理思考块造成的，决定当前先忽略，将调查与处理放到后续流式传输优化中，避免阻塞 s09 学习。

### 当前事实与待确认条件

- AnthropicSdkLlmClient.toResponse 目前只映射 text / tool_use，其它块逐块跳过并打印 SDK 包装类名。
- ContentBlock 这个类名不能证明具体块类型；“属于思考块”仍是待核实的假设，不记录为已确认根因。
- 后续结合流式事件与最终响应的组装，明确各块的展示、消息保留或跳过策略，验证工具调用不会丢失或重复执行。
- 调查不要求打印完整思考正文、认证信息或敏感响应；先用块类型与必要的脱敏结构确认现象。

### 2026-10-19 实施进展

用户现已批准并实施 Leader 的正文 / thinking 流式展示。适配器保留 thinking 与 redacted_thinking，
不再将这两种已知块当成未知块；其它未知类型仍报告具体类型，不输出完整 payload。
流式参数拼装失败、缺结束事件或内容块未闭合时不执行工具；签名与加密内容不展示。
队友、子代理的 thinking 隐藏但按协议保留，辅助请求继续非流式。

没有采集当时的真实响应，因此不追认旧 ContentBlock 警告全部来自 thinking。
详细范围、验证和未验证项见 [流式输出任务单](../../jobs/s13/streaming-output.md)。

状态：**协议处理与展示已实现，工程自审与离线/PTY 检查通过，真实后端验收待用户执行**。

## OPT-005：减少任务说明中编造、过期或互相矛盾的任务 ID

### 问题来源与动机

2026-10-18 s13 Team 真机验收中，Leader 连续两次在新任务描述里写入不存在的 task ID，
随后在派工邮件中再声明“前一个 ID 是笔误”。队友识别矛盾并使用真实派工信息提交，
因此这两次报告最终关联正确，但不应长期依赖模型自行发现并纠正身份引用。

### 当前事实

- create_task 由程序生成 ID，模型在创建前撰写 description 时还不知道本任务真实 ID。
- assign_task / submit_task_result 的实际关联由结构化参数和程序保存的派工记录确定；
  本次未发现 Harness 将报告关联到错误任务，不能将描述错误记录为已经发生的任务串线。
- 自由文本里重复要求填写 task_id、另发进展邮件，既容易产生矛盾，也可能重复通知；
  正式 submit_task_result 已负责保存报告、更新状态并通知 Leader。

### 优化目标与候选方案

- 本任务身份和派工编号尽量由 Harness 统一附带，避免模型在描述或示例中预填尚未生成的 ID。
- 工具说明与角色提示明确：只使用工具真实返回的编号，不猜测；正式结果提交后无需默认重复发信。
- 必须引用其它任务时使用真实查询结果；保持任务 ID、派工 ID 和旧报告校验，不以文本替换掩盖错误。
- 是否增加文本矛盾提示另行决定，不机械替换正文里的所有编号，也不重写历史任务说明。

### 验收方向

检查新任务创建、再次派工和结果提交：模型无需在 description 中重复声明自身 ID，
队友仍可获得可靠身份；旧派工报告不能改变新派工状态。分别验证结构化关联与模型生成文本，
不将“这次队友猜对了”作为长期正确性保证。

状态：**用户确认的优化候选，未实施**。本次终端美化只记录此项，不改变任务协议或提示词。

## OPT-006：Linux 沙箱与权限审批分离

### 问题来源与动机

2026-10-20，用户希望减少重复命令审批，并参考 Claude Code 与 Codex 的权限研究重新设计审批链路。
讨论发现：命令关键词和目标路径检查可以筛选部分操作，却不能证明任意构建、脚本或复合命令的所有副作用。
逐条询问会频繁打断；直接放行又不等于操作被限制在工作区。希望以后通过实际执行限制减少对人工确认的依赖。

### 当前事实与范围裁决

- ShellCommand 通过 setsid 建立进程组，管理输出、超时和退出清理；进程组不是文件系统或网络沙箱。
- 文件工具直接使用 Java 文件 API；不能只限制 shell，就声称所有工具都受同一套沙箱保护。
- 当前命令/路径权限检查属于应用内判断，不提供任意子进程的系统级隔离。
- 用户明确要求暂不接入 Linux 沙箱。当前权限方案只讨论应用内规则与审批，不能以“只读沙箱”或
  “工作区沙箱”名义提供尚未落实的隔离，也不因选择“不询问”就宣称获得了受限自动执行。

### 优化目标与候选方案

- 将实际执行权限（读写目录、联网能力）、审批策略（按需询问/不询问）与审查者分别表示，界面提供常用组合。
- 将来评估 Linux 本地与 SSH 环境可用的操作系统沙箱方案，不在本条选定或安装后端。
- 普通命令在已授权范围中执行；扩大目录或网络权限需单独授权，命令允许规则不应隐式移除沙箱。
- 主 Agent、队友、一次性子代理及同步/后台命令采用一致的执行限制；内置文件工具也遵守同一权限配置。
- 工具进程的网络限制与 JadeCode 自身模型请求分开考虑，不能为限制命令联网而误阻断 Harness 的模型调用。

### 待确认条件与验收方向

- 沙箱后端、平台依赖、允许的读取/写入范围、临时目录及受保护元数据；不因名为“只读”就隐含全盘可读。
- 内置 Java 文件操作如何执行权限检查，以及符号链接和执行前目标变化的处理，不把路径比较当作万能隔离。
- 验证目录越界写入、网络限制、后台/子代理继承及清理；工具不能通过换执行方式绕过限制。
- 沙箱不可用或无法表达目标配置时明确失败/禁用该预设，不静默回退到宿主机完全访问。
- 区分普通业务失败与权限拒绝；不自动扩大权限重跑任意命令，以免重复已经发生的副作用。
