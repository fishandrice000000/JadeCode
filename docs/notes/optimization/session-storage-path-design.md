# 会话归档与工具结果转存路径设计

日期：2026-10-13。
状态：设计建议，尚未实施；不代表已批准改变 s08 的压缩、失败或恢复契约。
问题来源：父子 Agent 共享存储目录时如何明确文件归属，以及如何避免每次摘要都产生难以追踪的归档。
相关候选：[优化清单 OPT-002 / OPT-003](optimization-backlog.md)。本文件不是用户答题区，也不替代实施阶段的 jobs。

## 1. 从 Claude Code 借鉴什么

本次参考的是本机 `claude-code-2.1.88-source` 源码快照，不推断所有版本或所有特性开关下的实际行为。

- `src/utils/sessionStorage.ts` 的 `getTranscriptPath` / `getAgentTranscriptPath`：主会话用 sessionId 标识，子代理日志额外按 agentId 区分。
- `src/utils/toolResultStorage.ts` 的 `getToolResultsDir` / `getToolResultPath`：工具结果按会话组织，文件身份来自调用 ID，不是被读取的源文件名。
- `persistToolResult` 使用 `wx`；复用同 ID 文件依赖源码声明的“每次调用 ID 唯一，给定 ID 的正文确定”前提。
- 持续会话日志与超大工具输出是不同职责；该快照的时间型 Microcompact 不负责逐项先落盘再删除。

借鉴的是“稳定会话身份、明确记录归属、日志与正文职责分离”，不是照搬全局 `~/.claude/projects/` 路径或压缩行为。
尤其不能因为 Claude Code 的子日志分开，就宣称其工具结果也必然逐子代理分目录：上述工具结果路径函数本身没有 agentId 参数。

## 2. JadeCode 当前事实与设计边界

- 当前存储根为 `<workspace>/.transcripts/` 和 `<workspace>/.task_outputs/tool-results/`。
- TranscriptStore 保存的是压缩时传入的消息快照，不是整个会话运行期间持续追加的事件日志。
- 两个存储类用 `createTempFile` 创建独立文件；现有父子转存不会因为共用目录而相互覆盖。
- 现有工具 ID 校验保证同一批次内不重复，没有建立“跨整个会话永久唯一”的存储身份契约。
- Micro / snip / history 等仍按现有契约先完成保存，再返回替换历史；路径设计不改变此顺序。

因此本方案首先解决归属与回查；持续日志、恢复会话与减少摘要快照数量是后续独立能力，不能靠改目录假装已经具备。

## 3. 推荐目录

沿用两个已经存在、已经被 Git 忽略的工作区存储根，不新建全局项目路径编码机制。

```text
<workspace>/
├── .transcripts/
│   └── <sessionId>/
│       ├── session.json
│       └── agents/
│           ├── main/
│           │   ├── compact-snapshots/
│           │   │   └── transcript-<snapshotId>.jsonl
│           │   └── events.jsonl                 # 未来持续日志；本轮不实现
│           └── <agentId>/
│               ├── compact-snapshots/
│               │   └── transcript-<snapshotId>.jsonl
│               └── events.jsonl                 # 未来持续日志；本轮不实现
└── .task_outputs/
    └── <sessionId>/
        └── agents/
            ├── main/
            │   └── tool-results/
            │       └── <safeToolUseId>-<outputId>.txt
            └── <agentId>/
                └── tool-results/
                    └── <safeToolUseId>-<outputId>.txt
```

两棵目录使用同一组 sessionId / agentId，分别回答：

- `.transcripts`：这段对话或压缩快照属于谁？
- `.task_outputs`：这份已转存的工具正文属于谁？

`compact-snapshots` 明确表示“压缩时保存的历史快照”，避免把它误解为完整持续会话日志。
`events.jsonl` 仅预留未来职责，不创建空文件、不据此宣称支持会话恢复。

## 4. 三种身份各自代表什么

### sessionId：一次顶层对话

由 harness 创建，不由模型指定，不使用 PID、Java 线程 ID 或时间戳单独充当身份。
建议使用随机 UUID，并在创建会话目录时防止既有会话目录被误当成新会话复用。

- 一次 `jade run` 是一个新顶层会话。
- 一次 `jade repl` 从启动到退出属于同一会话；用户每次输入不重新生成 sessionId。
- 未来恢复会话时，加载已保存身份，不生成新 ID 后假装接续原会话。

### agentId：该会话中的独立执行上下文

主循环使用固定名称 `main`；每次新的子委派生成独立 agentId，并继承顶层 sessionId。
因此父子归属键是 `(workspaceRoot, sessionId, agentId)`，子代理不必额外伪装成新的顶层会话。
未来若支持继续同一个子上下文，继续使用原 agentId；新委派即使 prompt 相同，也不是同一个上下文。

`session.json` 记录格式版本、工作区根、sessionId 和创建信息，以及 agent 的父子关系。
可记录子委派来自哪个父 agent / 哪次调用；这只是归属元数据，不把父消息历史复制给子代理。

### outputId / snapshotId：一次成功发布的落盘文件

第一步沿用当前“安全 ID 前缀 + 排他创建的随机后缀”机制：不会覆盖，原始 toolUseId 只是可读线索。
文件名不使用 `example.md`，因为同一源文件可以被不同参数、不同版本或不同 Agent 多次读取。

暂不改成 `<toolUseId>.txt` 并在已存在时直接跳过写入：当前契约不足以证明同 ID 跨批次必然对应同一份正文。
后续若需要“同一次调用反复压缩只保存一次”，先引入可跨压缩保留的调用记录身份与结果引用。
同一实际调用可复用旧文件；新的实际调用即使参数和正文相同，默认仍有独立记录。

## 5. 工作区根与调用方绑定

`workspaceRoot` 来自 CLI / harness 明确确定的工作区，进行规范化，并在会话内保持稳定。
不是 Bash 某条命令的临时 cwd，也不自动推断为 Git 根目录；非 Git 项目与子目录工作区同样可能有效。
工作区已经提供项目命名空间，所以无需再把绝对项目路径编码成目录名。

创建顶层会话时确定 sessionId；进入某个 Agent 上下文时确定 agentId，计算这两个目录：

```text
transcriptDir  = <workspace>/.transcripts/<sessionId>/agents/<agentId>/compact-snapshots
toolResultsDir = <workspace>/.task_outputs/<sessionId>/agents/<agentId>/tool-results
```

存储目录必须由调用方身份确定，不能按“当前正在执行哪个 Java 线程”猜测。
现有 ContextCompactor 在构造时绑定目录，因此实施时不能继续把一个固定目录实例直接用于所有 agentId。
可以按 Agent 归属装配存储依赖，复用同一套压缩实现、LLM client 与适用阈值，不复制算法或临时切换全局目录。

若未来允许子 Agent 在另一工作区工作，需要为目标工作区显式建立存储上下文；父侧保留委派关联。
跨工作区恢复路径的访问能力需要另行设计，不能因为存在父子关系就自动授予读取另一工作区的权限。

## 6. 保存与恢复契约

- 排他创建且不覆盖已有文件；清洗后的 ID 碰撞不能复用别人的结果。
- 完成正文写入并关闭文件后才返回路径、替换模型可见正文；失败时保持现有明确失败行为，不返回虚假恢复路径。
- 普通写入成功不等于承诺断电后绝不丢失；若以后需要此等级的持久性，必须明确同步落盘策略及验证。
- 对模型继续提供可通过已有工具读取的绝对路径，不仅提供一个尚无解析能力的 opaque ID。
- 当前可信 marker 的真实路径检查继续保留；目录分组不是权限隔离，也不能证明任意文件内容确由 harness 生成。
- 本 Agent 的文件按自己的目录识别；读取父 / 兄弟 / 其它工作区材料不是自动继承的权限。
  若未来明确传递了授权的结果引用，应同时明确恢复访问及可信 marker 识别范围，不能只扩大到整个工作区当作解决方案。
- 不移动旧文件来修饰目录：历史 marker 引用的旧绝对路径应继续有效。若需跨版本恢复，另行设计版本化兼容入口。
- 不因为会话结束就自动删除文件；恢复引用仍可能被其它已保存材料使用。清理策略单独讨论与授权。

## 7. 持续日志与工具正文共享：后续才决定

### 减少每次摘要的新快照

仅改路径仍会每次创建压缩快照；解决文件数量需要新增持续日志机制，而不是把同一个 transcript 文件反复覆盖。
未来可让 harness 记录原始消息及压缩事件，压缩器返回该 Agent 日志路径和稳定范围标识。
日志与模型请求历史各自演化：日志记录原始事实，模型历史可以变为摘要；不能把已摘要的列表反复追加当作完整原始日志。

替代现有压缩快照之前，必须保证将被移除的消息已写入可恢复日志，且所有引用的工具结果正文存在。
异步“加入队列”不足以满足此条件；如采用异步写入，应在有损替换前等待必要写入完成，失败时不能假装已有恢复副本。
禁用日志时不能静默退化为直接丢正文，需要保留快照路径或明确拒绝依赖日志的压缩行为。
这些契约需要新任务单与测试，不在目录组织步骤顺带实现。

### 是否共享相同工具正文

本阶段推荐逐 Agent 保存，暂不采用工作区级内容寻址对象库。
它更直接，也不需要先引入共享对象索引、完整性校验、引用生命周期和授权范围。
这不表示父子结果永远不能共享；后续若证实磁盘重复成本值得优化，可保留独立调用记录，另行引入不可变正文共享。
该优化减少磁盘重复，不自动减少发送给模型的 token，也不自动允许跳过工具执行。

## 8. 实施建议与验证边界

第一项能力只实施稳定身份、按归属装配目录和必要元数据；保留现有压缩算法、marker 形状、排他新建与失败语义。
不同时实现持续日志、恢复 CLI、内容哈希去重、Read 输出缓存、自动清理或新的并发协调系统。

验证应覆盖：REPL 多轮同 session、多个子委派不同 agentId、相同 ID / 清洗碰撞不覆盖、不同工作区归属正确、
重复压缩复用可信引用、目录或写入失败不返回假路径、路径与符号链接围栏不退化，以及现有父子压缩回归。
旧文件不搬移，旧 marker 的兼容读取范围如需扩大必须先裁决，不能以迁移名义跳过安全检查。

本轮仅完成设计与候选记录；没有修改源码、创建运行时存储目录、搬移既有文件或执行 Git 提交。
