## 1. 为什么有 TodoWrite，还需要 Task System？

假设 Agent 要交付“登录功能”，拆成数据库结构、API、测试三个工作。
TodoWrite 可以把它们列出来，模型也能自己想出顺序；但进程退出后清单消失，而且“应该先做数据库”
只是模型对计划的理解，没有成为 Harness 可以检查的状态。

s10 把这些关系持久化：任务有稳定 ID，API 的 blockedBy 指向数据库任务，测试依赖 API。
模型仍负责拆解和选择行动，Harness 负责检查“所认领任务的前置条件满足了吗”，并保存实际状态。
它不是替模型设计工程，而是让模型提出的协作计划有一个可检查、可恢复的载体。

| 机制 | 保存什么 | 主要用途 |
| --- | --- | --- |
| TodoWrite | 当前行动清单 | 让模型持续更新自己的计划 |
| Memory | 跨任务可复用知识 | 新任务重新获得有关偏好和项目背景 |
| Task System | 具体任务的状态、责任与依赖 | 恢复未完成工作，判断哪些任务能被认领 |

## 2. 模型决定什么，Harness 保障什么？

模型决定目标怎样拆分、依赖怎么安排、哪个任务值得先做，并通过工具提出操作。
Harness 检查 ID / 文件 / 状态与依赖图，执行合法变更。它不会自己去写 API，也不会仅凭 subject
判断“数据库真的已经创建正确了”。completed 是被接受的状态声明，不是工程验收证明。

典型数据流：

```text
模型创建节点 → 工具返回实际 ID → 模型添加依赖 → Harness 验证并保存
                                                    ↓
       读取进度 ← 完成并报告解锁 ← 执行真实工作 ← 认领可开始的任务
```

“解锁”只表示前置条件满足，不等于任务已经自动执行；具体选择仍来自模型或未来调度机制。
跨会话恢复的是任务状态和描述，不是完整聊天、工具调用证据或已完成工作的正确性。

## 3. 为什么先创建，再加依赖？

工具 ID 在执行时生成，而模型在一条回复里已经写好了整批调用参数。
即使 Harness 顺序执行三个 create_task，第二个调用的参数也不会自动获得第一个工具结果。
因此模型先收齐返回 ID，下一轮再调用 update_task。这个设计适应真实 Agent 工具数据流，
不靠模型猜随机 ID，也不假定工具调用之间存在参数变量替换系统。

## 4. 状态机不是并发协调服务

`pending → claim → in_progress → complete → completed`。
claim 需要全部前置任务完成；complete 需要状态与 owner 匹配。
owner 表示负责者，本章原课程工具默认使用 agent 标签，不提供真实身份认证。
两个并发进程同时 claim 的冲突并不是顺序检查天然解决的；本章不提前实现后续团队协作。

现有工具 task 的含义仍是“委派给子代理”，不是“创建持久任务”。两者可以以后结合，
但新建任务记录不会自动启动子代理，子代理结束也不会天然等于对应任务通过验收。
