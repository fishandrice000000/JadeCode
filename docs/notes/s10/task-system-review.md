本轮交付“持久任务图与顺序状态流”，不是并发调度或完整崩溃恢复系统；十文件本地提交已获批准，独立真机验收待完成。

## 1. 需求与职责先行

你给出的任务图：B、C 依赖 A；D、E 依赖 B；F 依赖 C。
模型负责提出这个拆分，Harness 负责保存它，并在 claim_task 时拒绝尚不具备条件的任务。
否则模型即使把计划列得很完整，依赖顺序仍只存在于它的理解里，程序无法据此拒绝提前认领。

这套系统不要求隐藏暂时不能做的任务。list_tasks 仍返回全局进度，方便模型理解后续目标；
工具层负责检查操作是否合法。直接绕过任务工具去编辑文件不被任务图物理拦截，认领也不是启动执行。

completed 是任务管理状态，不是可信质量证明；newlyUnblocked 是新获得开始资格，不是已调度。
状态和责任标签能够恢复，但具体做到哪一步仍需结合实际源码、运行材料和验证判断。
这些是 Task System 的边界，不要求在 s10 额外实现锁、审查器或断点续跑引擎。

## 3. 原课程与 JadeCode 的取舍

原课程的核心：任务 JSON、稳定 ID、先建节点后连边、防环、认领 / 完成、返回刚解锁任务。
JadeCode 保留它的顺序状态流与固定 agent 负责者，未提前实现团队身份或抢单。

Java 侧增加不可变值、严格文件 / 参数结构检查、拒绝记录软链，以及旧任务的临时写入后原子替换。
完成操作先在快照里算好返回结果再保存，成功后不额外读磁盘；普通写入失败不会原地截断旧 JSON。
这不等于多进程互斥、断电耐久或可以证明无副作用重试；没有 fsync / 锁 / 恢复日志。

## 4. 三个具体场景问题

T01 / T02 概念题已经在对话中讲解，不要求重答。以下围绕实际 Agent 工具数据流，可分批讨论。

### P01：为什么模型不能在同一批调用里“顺便接好整张图”？

模型的一条回复同时创建 A、B、C，但 ID 都由工具执行时生成。
如果同一回复中的 update_task 写一个猜测 ID，会发生什么？下一次模型请求为什么才具备正确连边的信息？
请结合 tool_use → tool_result → 下一次正式请求说明，不用解释 Java 集合。

回答： 

这是因为 ID 只在工具执行时才生成. 跟 create_create 同一批调用的 update_task 并不能知道那些任务的 ID, 从而不能拼接整张图.

### P02：B 没被“刚解锁”再次报告，是否意味着它不能做？

A 已完成，B、C 解锁；模型选择先做 C，C 完成只返回 F。
B 此刻到底是什么状态、能否认领？为什么“本次新解锁的任务”不能当成“全局全部可开始的任务”？
如果模型忘了 B，应调用哪类任务工具恢复全局视野？

回答：

并不意味着不能做. 本次新解锁的任务只表示有哪些新任务能做, 不作为全局可用任务的列表. 想要知道所有任务, 应该调用 list_tasks.

### P03：可后补——新任务为什么不会自己开工？

用户只让 Agent 创建 A–F 的计划，不要求现在实现。六项记录都创建、依赖也连好了，A 没有前置条件。
为什么 Harness 不应仅因为 A 可开始就自动派子代理？从“用户授权的目标”和“任务记录的职责”解释。

回答：

"现在能做"不等于"应该现在做". 所以不会也不应该自动开工. 开工的时机应该由模型或用户来定夺.

以下是用户选择执行的步骤，不由 ChatGPT 调真实 API。建议使用专用空工作区；确认 CLI 脚本、配置与工作区实际位置。
除 .tasks 外，现有 Memory / 上下文保护也可能写运行目录，不能把“未调用 write_file”当成进程完全只读。

1. 要求只登记 A–F 图，不执行实际工程；让模型先创建取得 ID，再按上述关系添加依赖，最后列举确认。
2. 明确要求尝试认领 B，观察工具的阻塞错误，而不只看模型口头说“它被阻塞”。
3. 要求认领 A；本次把 A 定义为“人工确认依赖图已建立”，用户确认该检查完成后再登记 A 完成。
   检查完成结果仅新解锁 B、C，且 B/C 仍为 pending，没有自动启动子代理。
4. 退出并重启 CLI，用 list_tasks / get_task 检查实际 ID、完整说明与状态仍在；无需真的实现登录功能。
