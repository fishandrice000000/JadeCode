## Q01：已有请求前整理，为什么还需要失败后的分类？

设未来循环已经在模型调用前执行 `prepare`，本地估算认为上下文未超限，但正式 API 仍返回 `prompt_too_long`。

解释本地估算与服务端拒绝为什么可能不同；指出 `isContextOverflow` 应放在这一轮数据流的哪个位置。它返回 true 时，是否已经完成了消息压缩或模型重试？

回答：

1. 不同原因: 本地估算是通过字符串长度来估测 Token 数量, 但是服务端的长度是使用 Tokenizer 算出来的 Token 数. 前者相对于后者肯定会有误差. 同时实际请求也包含系统提示词和工具定义等内容.
2. 位置: 应该放在调用部分 `try {client.completeA();} catch(LlmException e) {if(isContextOverflow(e)) {reactiveCompact()}}`
3. 返回 true 时应该只表示放行对消息进行压缩后再重试, 而不表示已完成这一过程.

## Q02：哪些失败值得改变上下文？

按当前契约分别判断下列外层异常说明是否打开压缩补救开关，并解释为什么不能只按 HTTP 400/429 决定：

1. HTTP 400，说明是 `prompt_too_long`。
2. HTTP 400，说明是 `invalid_request_error: malformed tool input`。
3. HTTP 429，说明是 `too many requests`。
4. 外层说明是 `request failed`，只有 cause 写着 `too many tokens`。
5. 外层说明是 `context_length_exceeded`。

假如真正的超限错误使用了第 5 种措辞，当前方法会怎样？再比较“漏判超限”和“误把限流当超限”对 Agent 行为、历史保真和额外调用成本的影响。这里的 false 能否证明上下文一定不长？

回答：

1. 只有 1, 即返回 true 并进行压缩+重试. 400/429 并不一定意味着当前请求失败原因是上下文过长,
2. 当前方法不会放行. 尽管我不知道为什么要这么设计, 明明出于兼容性完全可以加上这种模式匹配.
3. "漏判超限"会让本来可以通过压缩挽救的一轮运行, 被当作普通失败而直接中止了. "误把限流当超限" 会导致 Agent 额外进行本没有必要的压缩, 降低历史的保真度, 同时可能导致额外的压缩请求调用而产生额外的调用成本.
4. false 不能证明上下文一定不长. 可能是一个过长的历史正好遇到网络问题没发过去. 这种情况下就会等到网络正常, 上下文成功发送过去后, 等到服务器报超限时, 再判 true 来进行压缩.

## Q03：为什么分类方法不能承诺恢复成功？

设正式请求因超限失败，分类返回 true，但摘要调用失败；另一种情况是摘要成功，下一次正式请求仍然超限。

说明未来恢复链路为什么需要原文归档、受限重试和明确的失败出口，为什么不能只要 true 就无限重复压缩。最后指出：本轮 6 条测试证明了哪项能力，哪些真实 Agent 行为仍需要后续实现与集成验证？

回答：

1. 这个恢复流程的内容大致如下:
   1. 正式请求失败, 分类确认是否应该压缩后再重试
   2. 保存完整的原历史, 随后据此生成摘要.
   3. 摘要生成成功后, 构建压缩后的历史, 重试正式请求.
   4. 如果再次失败, 看剩余重试次数决定是否还要重试.
2. 原文归档的意义: 根据历史获得的摘要是信息有损的, 需要原历史来做留档查找.
3. 受限重试的意义: 即使摘要获取成功, 也不能保证下一次正式请求能通过. 因为它保留的尾部, 当前请求或者其他请求内容仍然可能太大. 无限重复压缩在此时不一定能保证总会成功, 因此为了避免出现重试死循环的情况, 需要进行重试次数的限制.
4. 明确的失败出口的意义: 对于摘要失败的异常, 需要特殊处理. 因为此时无法进行"根据摘要内容构建压缩后的历史"的过程. 所以需要特殊处理这种异常, 摘要调用抛异常时，保留原历史、停止补救、明确传播失败. 不能用假摘要继续替换历史并重试.
