## 一、入口生命周期与职责（关键理解题）

### Q01：为什么 USER 不等于人类请求？

分别描述人类输入与工具结果在消息列表中的角色和内容块形态。举一个“角色是 USER，但不能作为 activeRequest”的例子。只检查 role 会漏掉什么？

回答：

对一个 ToolResultBlock 的 Message 来说, 它的 role 就是 USER, 但是并不是人类请求, 而是用户端 Harness 自动发来的消息.

只检查 role 的话, 就会把只含工具调用结果的 Message 当作人类请求.

### Q02：为什么入口捕获一次，而不是每轮重新提取？

设一次 run 先收到“修改 A”，随后执行工具并追加结果，最后 Stop hook 又追加一条 synthetic user 消息。说明三个时刻最后一条消息可能是什么，以及重新提取会造成什么错误。未来调用方保存 `final` 局部变量的目的是什么？`final` 能证明这句话由人类发送吗？

回答：

synthetic user 消息就是在某些情况下比如说`/goal`时, Harness 自己添加的 User prompt.

我猜测最后一条消息会是那个 synthetic user 消息.

如果重新提取, 那么这条消息就会变成新的 active request. -- 这与目标不符.

`final`的作用是如果局部变量存储了正确的人类请求, 那么它之后不会再被改变. 但是存储人类请求的正确性它并不能保证.

我的理解: 之所以只在入口捕获一次, 是因为 query (人类请求) 实际上只会出现在调用 `loop.run()` 之前一次. 所以只进行这一次捕获就够了. 如果每轮重新提取, 那么只会徒增覆盖有效 active request 的风险.

### Q03：它为什么拒绝末条，而不向前寻找旧请求？

历史中有一个合法人类请求，但末尾是一条工具结果。本方法为什么不“帮忙”回退到前面的文本？结合方法契约解释：它是在恢复任意历史里的请求，还是在检查一次新运行的入口？遇到非法入口时，返回旧请求与抛异常各会让调用方观察到什么？

回答：

这个方法的用处是寻找**当前最新**的人类请求, 而非历史中最近的人类请求. 而在一次 run 的开始时, 当前最新的人类请求只可能在消息列表的末尾. 因此如果最后一条不符合要求, 那么直接拒绝即可.

### T01：为什么 null 测试用了 Arrays.asList？

比较 `List.of`、`List.copyOf`、`Arrays.asList` 与 `new ArrayList` 在测试中构造 null 元素、可修改集合时的区别。若测试在创建列表时就抛错，能否证明待测方法处理了 null？

回答：

这几个方法在集合构造和修改方面不同：

| 写法                            | 允许 null 元素 | 替换元素 set | 增删元素 |
| ------------------------------- | -------------- | ------------ | -------- |
| `List.of(...)`                | 不允许         | 不允许       | 不允许   |
| `List.copyOf(collection)`     | 不允许         | 不允许       | 不允许   |
| `Arrays.asList(...)`          | 允许           | 允许         | 不允许   |
| `new ArrayList<>(collection)` | 允许           | 允许         | 允许     |

Arrays.asList 是由数组支撑的固定长度列表，不是完全不可修改的列表。

测试要构造“最后一个元素为 null”的输入。如果使用：

`List<Message> messages = List.of(Message.userText("hi"), null)`;

异常发生在准备输入时，不能证明 extractActiveRequest 如何处理 null。

所以测试用 Arrays.asList 先成功构造非法输入，再交给待测方法，验证它是否按契约拒绝。

另外，`List.copyOf` 和 `new ArrayList<>(collection)` 都不是深拷贝：不会递归复制每个 Message 及其 content

### T02：这是否是完整消息协议校验？

设末条是合法请求，但更早消息含孤立工具结果。本方法会不会扫描并拒绝旧历史？对比 `ToolExchangeProtocol.validateHistory` 的职责，说明为什么不能把一个方法的通过当成所有历史都合法。对于其它非文本块，本方法当前契约规定了哪些条件、没有规定哪些条件？

### T03：测试辅助方法怎样可能掩盖失败？

工程 Review 记录的一项非阻塞维护问题：测试文件末尾 `messageOf` 除了预期的 `IllegalArgumentException`，还捕获 `AssertionError` 并返回其文本。这不是推荐的异常类型验证写法；后续应由 worker 维护，不要求你改代码。

解释如果辅助方法将断言失败转换成普通字符串，测试可能失去什么保障。与 `assertThrows` 相比有什么区别？为什么这个建议不等于当前生产方法存在阻塞缺陷？

回答：

AssertionError 通常表示断言没有成立，应该让测试失败。

但当前辅助方法把它转换成普通字符串返回：

本应使测试失败的 AssertionError
→ 被捕获
→ 变成字符串
→ 后续测试继续检查字符串

如果字符串恰好满足后续检查，测试就可能通过，尽管它根本没有收到预期的 IllegalArgumentException。

更合适的写法是：

```Java
// 必须先确认异常类型正确，才能取出它的说明。
String message =
        assertThrows(IllegalArgumentException.class, call::run).getMessage();
```

这样，正常返回、NPE 或 AssertionError 都会使断言失败；只有预期类型或其子类才会通过。

这属于测试保障不够严谨，不直接证明生产代码错误。当前生产方法没有相关 AssertionError 路径，主要非法输入另有直接 assertThrows 测试，所以之前将它列为非阻塞维护建议。

### T04：静态方法与状态生命周期

解释 `public static` 在本方法中的意义：调用时是否需要构造一个压缩器实例，它有没有跨 run 保存请求的字段？若把 activeRequest 存成共享实例字段，连续 run 或父子循环复用时可能出现什么问题？这与“参数列表中的消息是否可变”是同一个问题吗？

回答：

两个关键字分别表示：

- public：其他包的代码可以调用。
- static：调用属于类，不需要先构造压缩器实例。

当前方法可以直接这样调用：

```Java
// 请求保存在本次 run 的局部变量中，不写入共享压缩器。
final String activeRequest =
        ContextCompactor.extractActiveRequest(messages);
```

它只读取参数并返回字符串，没有把请求保存到跨 run 存活的字段里。注意，这不是 static 自动保证的，而是当前实现没有使用共享状态。

如果把请求放进共享压缩器的实例字段，可能出现：

- 下一次 run 忘记更新字段，沿用上一次请求；
- 父循环保存请求 A，子循环复用同一实例并写入请求 B；
- 子循环返回后，父循环再读取字段，拿到的是 B。

即使没有并发，父子调用嵌套也可能覆盖共享字段。局部变量则属于各自那次方法调用，父子请求不会互相替换。

最后，这是两个独立问题：

> 请求存在哪里、存活多久，是状态生命周期问题。
> 是否修改传入的消息列表，是输入副作用问题。
