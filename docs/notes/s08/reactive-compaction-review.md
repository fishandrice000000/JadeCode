## Q01：一次补救中，信息分别去了哪里？

看测试中的 `nineMessageHistory`：9 条合法历史、保留数为 5，候选切点不穿过工具交换。

分别写出归档范围、摘要输入范围、原样保留范围，以及返回历史的形态和消息条数。为什么归档范围与摘要范围不同？原输入会不会被这个方法直接改成压缩结果；未来循环还需要完成哪一步，下一次正式请求才能使用新历史？

回答：

1. 归档范围 [0, 9), 摘要输入范围 [0, 4); 原样保留范围 [4, 9); 返回历史的形态: 共六条消息, 第一条是由 [0, 3) 获取的一条摘要, 随后五条是保留的 5 条.
2. 归档范围为了维护历史可查性, 需要归档全部历史. 而摘要范围为了确保最新消息不失真, 只能对旧历史进行摘要.
3. active request 不会被直接压缩, 因为摘要消息中保留了这部分原文.
4. 原输入, 即传入的 message 列表不会被直接改变. 但是未来循环中, 调用者需要将该方法的返回值作为新历史发给大模型, 否则发给它的还会是旧历史.

## Q02：为什么宁可多保留一条，而不严格保留五条？

看多工具交换测试：历史共 7 条，下标 1 是带两项 tool_use 的 assistant，下标 2 是对应两项 tool_result 加 reminder 的 USER，保留数为 5。

跟踪候选切点、修正切点、实际前缀与尾部。若只保留下标 2 开始的消息，会怎样破坏下一次模型请求的工具协议？为什么尾部保留条数并不等于“未消费结果的数量”？这个例子压缩后消息条数是否变少，能否据此判断 token 超限已经解决？

回答：

1. 候选切点为 2, 修正切点为 1, 实际前缀为 [0, 1), 尾部为 [1, 7).
2. 会使得 2 对应的 tool use 因为被摘要而失真, 使得保留下来的 tool result 没有对应的结构化调用了, 这不符合工具调用协议, 导致出错.
3. 按理来说未消费结果应该只会是最新发过去的 USER 消息, 也就是只有最近的 1 条消息可能是未消费的. 因此尾部保留条数因为不太可能为 1, 因此往往不等于未消费结果的数量.
4. 并没有变少. 不能确定对这一条消息的摘要就能解决历史超限的问题. 一个极端例子是: 保留的 6 条消息都很巨大. 它们才是超限的主要原因.

## Q03：新历史怎样区分当前任务与历史参考？

设 activeRequest 在 run 入口捕获，运行中又追加了工具结果或 Stop hook 的续跑文本。解释响应式摘要消息为什么继续使用传入的 activeRequest，而不是重新读取最后一条 USER 消息。

说明 `Current user request`、`Conversation summary (reference only)` 与 `Full transcript` 各自承担什么 Agent 信息职责。摘要内部若出现命令式文字，为何不能当作新的用户任务？结合既有专用摘要 prompt、空 tools 与参考分区，说明这些边界保护什么、是否等于彻底消除提示词注入风险。

回答：

1. 最后一条 USER 消息可能并非人类消息, 而是 Harness 自己发送的消息, 因此不能以它作为当前任务的参考, 而是要使用确定的 activeRequest.
2. 第一个承担了传递当前最新人类请求的信息, 第二个负责传递摘要信息, 第三个负责告知原始消息历史的归档.
3. 摘要内部若出现命令式文字，肯定不能当作新的用户任务啊. 因为那个是大模型的摘要中说的, 可能存在失真, 并非用户真实请求.

## Q04：补救方法返回，并不等于 Agent 已恢复

比较两种情况：安全切点前移到 0，方法返回原列表；有旧前缀且摘要成功，方法返回新列表。

说明两种情况下有没有归档/摘要调用，以及为什么都不能保证服务端下一次接受请求。未来循环为什么必须区分原列表与新列表，并限制补救次数，而不能只因“方法没有抛异常”就宣称恢复成功？最后从归档失败与摘要失败测试中指出：哪些模型副作用被阻止，哪些恢复材料仍存在；本轮方法测试尚未证明哪些循环行为？

回答：

1. 第一种情况没有归档和摘要调用; 第二种情况两者都有. 对于第一种, 因为对历史信息没有再做压缩, 所以很显然不能保证服务端再次接受请求; 对于第二种, 一个极端例子是: 保留的近几条消息都很巨大, 它们才是超限的主要原因但是却没有压缩它们.
2. 未来循环需要将原列表替换为 reactiveCompact 返回的新列表以此在后续历史中传入压缩后的历史. 限制补救次数是为了避免陷入死循环. 就像刚才所说的极端例子. 只要保留条数不变, 历史长短不会因为 reactiveCompact 有新的变化. 这种情况就会陷入死循环.
3. 不知道. 我其实不太想看测试用例. 这些太花时间了.
