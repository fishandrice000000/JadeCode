## 1. 先看需求：准备过的请求，仍可能被拒绝

想象 Agent 刚改完文件、跑完构建，工具结果已经完整进入历史。
下一步需要模型判断：改动是否符合目标？是否继续修复？
harness 已经执行 prepare，但本地字符估算并不等于服务端 token 计算，
加上 system、工具定义、输出预算等因素，正式请求仍可能被以“上下文过长”拒绝。

如果没有补救，任务在这里中断；如果从头重跑整个任务，已经执行过的文件写入或命令可能再执行一次。
这次能力的目标是：**改变模型下一次看见的历史，重新请求下一步行动，不重做已经完成的行动。**
这与普通网络重试不同：有损压缩会改变模型可见证据，不能对每种失败都套用，也不能无限尝试。
它是 harness 的有限恢复策略，不是模型又主动调用了一次 compact 工具。

## 2. 它在整个 Agent 中的位置

只看这条恢复路径：

```text
完整会话 → prepare → 正式模型请求
                         │
                    匹配超限失败
                         ▼
               检查并消耗补救额度
                         ▼
        完整归档 → 辅助摘要旧前缀 → 候选历史
                         ▼
             采用候选 → prepare → 正式请求
                                      │
                                   成功回复
                                      ▼
                            原有工具 / Stop 主流程
```

循环决定失败如何分流、机会何时耗尽、候选何时成为会话；压缩器决定如何构造候选。
摘要模型只整理证据；主任务模型才继续决定业务行动。

“同一次请求”指同一个尚未取得主任务回复的逻辑步骤，**不是发送完全相同的字节**：
采用摘要后历史已经变化，重试前也会再经过 prepare。
正式请求成功后，Agent 执行工具，接着发出的另一个正式请求有新的补救额度。
因此额度不是“整个 run 只许补救一次”，也不跨下一条用户请求继承。

### 源码阅读时需要先澄清的措辞

AgentLoop 的 2.3 注释写“压缩器……不发请求”，少了“正式”二字。
正确理解：**压缩器会请求模型生成辅助摘要，但不重试主任务的正式请求。**
ContextCompactor.reactiveCompact 的 JavaDoc 已正确区分这两种请求；
此处源码措辞列为非阻塞维护项，尚未由 worker 校正，不要据此认为摘要完全不调用模型。

另外，reactiveCompact 保护的是“近期尾部”：里面可能同时有已消费和未消费的消息，
不能把它的整个尾部都理解成“模型从未读过”。切点会保护跨界的完整工具交换。

## 3. 为什么这样设计，而不是只有一种正确写法

- **先预防，再补救**：prepare 降低超限概率；收到匹配失败后再付出一次额外摘要成本。
  分类目前靠两个关键词，并不是服务端超限的完备证明。
- **给补救设上限**：避免模型摘要、费用、等待与信息损失无界增长。
  “最多一次”是当前策略，不是 Agent 协议规定；摘要后仍失败，要保留真实失败而不是假装继续成功。
- **近期尾部保真**：尽量不把模型正要使用的最新证据先转述掉。
  代价是尾部本身过大时可能没有足够空间；保真和请求能否成功不是总能兼得。
- **只重试正式请求**：准备、辅助摘要或工具失败有各自的原因和状态，
  不能统一包成“主任务上下文太长”并递归补救。
- **不回滚整次运行**：摘要候选成功返回之前不采用半成品；
  已采用后，第二次请求失败不会恢复旧历史，先前工具副作用和成功归档也不会被撤销。
  这里没有文件系统事务，更没有“所有失败都从最初重来”的契约。
