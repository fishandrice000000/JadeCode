## A01：已经有自动整理，为什么还让模型主动请求压缩？

设 Agent 刚完成一次问题调查，历史里积累了多个文件片段和探索日志，即将进入实现阶段；此时上下文还没达到自动压缩阈值。

为什么“上下文有多大”和“当前工作处于什么阶段”是两种不同的信息？在这个场景里，主动压缩希望改善什么，而不仅是避免 API 超限？
如果完全取消 compact，只保留按大小触发的 prepare，会失去哪一种调节能力？反过来，若模型频繁请求压缩，可能付出哪些代价？
最后说明：提出 compact 能不能作为“用户任务已经完成”的证明？

回答：

1. 主动压缩希望改善"已经被使用完不会再用到的信息占用上下文"的情况. 如果 A 已经实现了, 那么实现 A 的过程就可以抛弃一部分了.
2. 模型主动请求压缩时提供了另一种可选能力, 即让模型根据任务进展，请求把过程记录收束为工作状态, 把 "做到状态 A 的过程" 来整理为 "状态 A 已实现" 从而舍弃一些无用信息.
3. 不能. 这完全是两码事. 模型完全可以认为"当前的情况可以阶段性 compact 一下" 来调用 compact, 而不是一定要任务完成才这么做.

## A02：新证据和旧记录应该承担相同的压缩风险吗？

比较两种场景：Agent 只提出 compact；Agent 同批提出“运行测试 + compact”，随后测试返回包含具体失败原因的日志。

主任务模型在选择这批工具时，是否已经知道执行后产生的日志？如果立刻把整批结果摘要成“测试失败”，可能如何影响下一步代码决策？
结合这两个场景，解释 JadeCode 为什么区分纯/混合策略，而不是只说“代码调用了两个不同的方法”。

再比较两个替代方案：无论何种批次都摘要全部历史；无论何种批次都保留最新交换。各自在空间收益、信息保真和实现复杂度上有什么得失？
如果新日志本身就太大，“完整落盘 + 路径与预览”和“只留下语义摘要”对 Agent 后续查证原文有什么不同？

回答：

1. 不知道. 如果立即把整批结果都摘要成测试失败, 可能导致失败的错误信息丢失, 导致下一步决策丢失了一些重要已知信息. 所以对于最近尚未被消费的消息结果不应该直接被摘要, 而是要保留, 等到消费之后再在下一次摘要中被压缩.
2. 空间收益来看,  前者更能腾出更大的空间. 信息保真来看, 后者能保留一些重要新鲜工具结果的信息.
3. 前者允许 Agent 使用 grep 等工具详细查找日志内容; 而后者会导致日志信息丢失许多, 使得 Agent 查证需要先找 transcript 才能找到归档地址. 这就是为什么需要历史留档.

## A03：压缩是一个能力，还是循环里的一段特殊逻辑？

设未来父循环与子代理都需要主动压缩。现在要在两处复用同一套纯/混合策略，但它们仍分别拥有自己的任务、历史和执行过程。

你会怎样在 CompactTool、AgentLoop/子循环与 ContextCompactor 之间分配：表达压缩意图、确认允许执行、选择安全时机、选择压缩范围、生成新历史、采用新历史继续工作？
为什么把策略下沉到 compactor 有利于复用，却不意味着 compactor 应执行工具、管理整个循环或保存共享的当前任务？
用需求与职责来评价本次移动方法、内联回填的调整：它想改善什么，哪些可观察的 Agent 行为应保持不变？不要以“方法数量少了”作为唯一理由。

回答：

1. 表达压缩意图这种由 LLM 自主决策的选项应该由 CompactTool 来执行. 确认允许执行, 选择安全时机这种跟工具调用这一过程相关的, 以及采用新历史这种跟把历史发送到 LLM 手里的过程, 应该放在 AgentLoop 中. 选择压缩范围, 生成新历史这种跟压缩过程强相关的应该交由 ContextCompactor.
2. compactor 是多个 AgentLoop 实例共享的代码逻辑. 因此, 它不应该保存跟会话私有的信息. 工具调用, 循环管理, 当前任务都是某个实例私有的事, 所以不该归它管.

## A04：压缩失败为什么不能被当作工具任务失败重跑？（可后补）

Agent 已经成功修改文件并运行测试，然后主动压缩的摘要请求失败。

从用户期望的任务连续性出发，区分“工具任务已经产生的外部效果”和“整理会话历史的动作”。为什么不能把摘要失败解释成整批工具都没执行过，然后自动重跑？
原历史和归档分别帮助恢复什么；仅有磁盘恢复路径，是否等于模型下一次已经知道完整内容？
说明你希望 harness 在这个场景中保留哪些信息、暴露什么失败，而不是要求列异常类或逐行描述 catch。

回答：

1. "为什么不能把摘要失败解释成整批工具都没执行过，然后自动重跑？" 这是什么问题? 摘要失败为什么要解释成**整批工具**都没执行过? 要想不也是想单独重跑 comapct 工具吗? 怎么会想到重跑整批工具的. 其他工具又没出错, 工具结果都好端端在历史里了, 干嘛要重跑? 而对于 compact 工具调用后遇到的获取摘要失败的问题, 这确实需要考虑. 而且 `run()`中怎么没有调用 `prepare()`?
2. 原历史保留了工具执行完成后的会话状态，让压缩失败不至于把这份状态也破坏掉. 因为我不知道你说的"原历史"指什么. 归档帮助恢复长结果的全文信息. 不等于. 模型仍需要通过 read 工具来获取原文.
3. Harness 在这个场景中应该保留当前用户请求; 已完成的调用及对应结果，包括测试的实际输出; 尚未采用压缩候选的消息历史; 已成功写出的归档; 压缩失败的原因，以及可选择的后续动作.
   Harness 也应告诉用户失败发生在哪个阶段、哪些事情已经完成、当前还能从哪里继续.
