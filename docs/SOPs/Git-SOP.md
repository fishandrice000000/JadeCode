# Git 提交规范(SOP)

适用于 JadeCode 项目的全部 Git 提交。

## 1. 拆分原则:一次提交只做一件事

- 每个提交必须**原子、完整、可构建**:单独检出任意一个提交,编译测试都能通过。
- 拆分粒度 = **依赖顺序上的最小不可分批次**:无依赖关系的文件各自成提交;相互依赖的文件(如 sealed 接口与它的实现,成环)必须同批提交。
- 一个提交不混两个任务;不提交已知有问题的代码(空骨架、半成品、多余 import)。
- 禁止 fix-up:新改动若是在补完上一个提交,用 `git reset --soft HEAD~1` 合并重提;已推送的历史,改写 / amend / force push 须先征得同意。
- 探索性工作放 temp/、wip/、scratch/ 分支,不直接合并,另建干净分支按本规范重提。

## 2. 暂存纪律:只 add 相关文件

- 提交前先 `git status` 看全貌,明确本次变更的归属。
- 用 `git add <具体路径>` 逐个列出,禁止 `git add .`、`-A`、`--all`、`*` 一把梭。
- add 后必须 `git diff --cached --stat` 核对:暂存列表与预期一致才提交。
- 暂存错:`git reset HEAD <路径>` 撤销重来。
- 不属于本次任务的 stray 文件保持 untracked,上报后由所有者决定去留。

## 3. 提交信息

**subject**:
- 祈使语气,说明改了什么、描述行为或能力
- 不超过 72 字符,结尾不加句号
- 中文句式「动词+对象:说明」,如 `添加消息模型单元测试`、`初始化 Maven 项目骨架:依赖与构建配置`

**正文**:
- subject 完全自明时可省略;否则解释为什么:根因、修复理由(只写 diff 看不出来的)
- 不逐文件罗列改动,不赘述 diff 可见的实现步骤
- 不写"构建成功""测试全绿"——提交能存在本身就说明通过
- 只描述相对父提交的最终变化,不描述中间版本差异
- 只在真正不显然时才写:新测试命令/工具、复现所需的非标准配置、影响数据解读的异常约束

**其他**:
- 不署名、不提 AI 参与(项目约束)

## 4. 执行流程

1. **方案先行**:列出拆分批次(文件 + 顺序 + 独立性理由)与每批提交信息,经审批后执行
2. **按批次执行**,每批:`git add <具体路径>` → `git diff --cached --stat` 核对 → `git commit`
3. **总核**:`git log --oneline` 确认历史、`git status` 确认工作区

## 5. 反面清单

- `git add .` / `-A` / `--all` / 通配暂存
- fix-up 提交;未经同意改写已推送历史
- 提交空骨架、已知有问题的代码
- subject 超 72 字符 / 带句号;正文罗列文件、写"测试通过"

## 示例:消息模型的五批提交(按依赖顺序,每批独立可编译)

```
85c63f9 添加 Role 枚举:映射线上 user/assistant 角色
0d76589 添加内容块模型:text/tool_use/tool_result 三种块
80a6e18 添加 Message 消息记录:角色与内容块列表
5b53648 添加消息模型单元测试
```
