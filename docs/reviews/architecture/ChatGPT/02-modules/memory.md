# 模块审查：记忆生命周期与文件存储

## 机制与合理之处

记忆被拆成文件存储、召回、提取、整理和生命周期协调五个类。一次新任务召回一次；模型选择固定目录快照中的索引而不是任意路径；无相关记录与选择失败有不同结果，后者可关键词降级。背景有数量和正文预算，并注明来源及截断。结束时只提取长期知识，当前任务限制不应直接保存；子代理不自行维护库。

新增记录用 CREATE_NEW 避免覆盖已有同名文件，候选和索引失败时清理本次创建的文件；索引用原子替换。整理比较快照，拒绝覆盖观察期间已改变的库，也检查目标是否被快照外对象占用。IO 失败只告警，不抹掉主任务结果。格式检查并不保证记忆内容真实，README 对这一点说明准确。

证据前缀 `src/main/java/com/jadecode/`：`memory/MemoryManager.java:53–108`；`memory/MemoryRecallService.java:77–174`；`memory/MemoryExtractionService.java:76–150`；`memory/MemoryStore.java:77–118,136–199,219–250`。

## ARCH-004：记忆整理先删除旧库，缺少崩溃后的恢复提交点

**P1；有依据的潜在风险；分类：持久化可靠性风险。删除窗口已证实，崩溃后果未运行注入。**

整理阶段把新候选写入临时目录后，删除所有旧记录，再逐个创建新记录，最后才替换索引。旧正文只备份在内存映射中。若进程在删除和重建之间退出，下次启动的扫描只会看到部分库；索引原子替换不能保护多个正文文件。临时目录有新候选，但当前读取器不识别它，也没有恢复协议。

反向检查：可捕获 IOException 时会删除新建文件并尝试写回旧内容，而且保留 suppressed 错误；两次快照比较也能挡住部分并发变动。这些防护有实际作用，但不覆盖 SIGKILL、断电或恢复过程中再次 IO 失败。源码和已有任务单已经承认没有崩溃事务；这是已知边界在长期个人软件目标下应提升的优先级，不是声称过去验收造假。

**具体设计**：为记忆库采用代次发布：先在新 generation 目录写齐正文及目录，验证可回读，再原子替换一个 CURRENT 指针；读者只读当前代次，旧代保留到明确清理点。这样故障发生在切换前仍读旧库，切换后读新库。旧平铺 Markdown 保持迁移兼容入口，首次导入成功后再启用新布局，不直接移动或删除用户旧库。若不愿改布局，至少建立含旧正文的持久备份及恢复标记，但恢复状态更多、复杂度更高。原子切换只定义采用的可见性；若需要承诺断电持久，还须另定文件/目录同步落盘和文件系统保证，不能仅凭 ATOMIC_MOVE 宣称断电安全。

收益是让多记录更新有一个明确的采用点，能够人工恢复；范围 MemoryStore、扫描器、清理与迁移说明；成本中至高；回归风险是旧路径引用、用户手工编辑、跨文件系统原子操作及权限元数据。P1 因为自动整理涉及长期知识的整库删除，丢失难以自动重建。

证据：`memory/MemoryConsolidationService.java:65–102`；`memory/MemoryStore.java:253–317` 的 staging、删除、重建和回滚；`:77–118` 的重启读取。必须以后验证：删除后中断、写新记录中断、指针切换失败、旧代损坏和手工编辑冲突；本轮全部未运行。

## ARCH-015：库增长后，固定前缀目录和整库整理会形成召回盲区

**P2；有依据的潜在风险；分类：容量与可维护性风险。**

每次召回先读取全部记忆正文，目录按文件名排序，然后只把前 12,000 字符放给选择模型。末尾记录不参与选择，关键词降级也只在同一批 visible 记录中搜索。整理要求整个库的 JSON 不超过 20,000 字符，超过就直接跳过；而且仅在本次新增成功时尝试整理。随着库持续增长，整理可能再也无法执行，固定前缀外的知识则长期不可见。

反向检查：少量、简短记录不会触发，限制本来是为模型请求成本服务；不是说当前工作区已经丢失召回，也未读取用户实际记忆数据。召回最多五条及正文 20,000 字符能限制模型背景，但无法限制前面的整库 IO。

**具体设计**：让存储提供元数据目录和按 ID 取正文两种读取。先对全目录做有界候选检索（可从现有关键词打分开始），再给模型选择候选，最后只读选中正文。对整理采用相关小批次，明确保留未参与记录；不能把批次替换误用成整库替换。设置库大小、单条大小和持续不可整理的可见状态，不需要先引入向量数据库。若目录增长超出本地扫描成本再考虑索引版本。

收益是让预算不等于永久忽略后部记录，并降低每次入口 IO；范围 MemoryStore、Recall、Consolidation；成本中；兼容风险是检索召回率、合并边界与旧索引失效。P2 因为依赖库增长，当前小库仍可正常使用。

证据：`memory/MemoryStore.java:86–108`；`memory/MemoryRecallService.java:84–99,116–124,186–210`；`memory/MemoryConsolidationService.java:29–31,67–86`；`memory/MemoryManager.java:89–99`。

## ARCH-018：辅助记忆请求和发布没有继承会话取消信号

**P2；有依据的潜在风险；分类：资源与生命周期风险。**

父子正式请求和工具在返回边界检查关闭，但记忆入口和维护服务只接收字符串或消息，没有取消参数。在等待提取模型时关闭会话，如果网络稍后仍正常返回，服务还会保存新记录、继续整理，甚至再发起一次模型调用。运行器关闭后只等两秒且消费者为 daemon；进程随之结束也可能与 ARCH-004 的发布窗口重叠。

反向检查：关闭确实禁用了新的工具；这项问题限于记忆维护及辅助请求，不声称退出后仍会执行文件工具。网络是否响应中断取决于 SDK，当前接口没有强取消保证；若请求迅速抛错，路径不会继续。问题依赖“晚到成功回复”条件。

**具体设计**：让所有辅助服务接收只读取消/截止时间，在请求前、返回后和持久化发布前检查，取消后不发起下一阶段。由顶层宿主统一拥有 LLM 客户端生命周期；先明确停止新请求与取消已发请求是两个能力，再按 SDK 支持程度实现。不要通过持有整个 SessionRuntime 来实现取消，也不要让记忆服务自己关掉父子共用客户端。

收益是关闭语义一致，减少晚到 IO 和额外调用；范围共享执行契约、MemoryManager 及三个辅助服务，未来可覆盖摘要；成本中；兼容风险是任务完成后取消时到底允许保存多少维护结果，需要明确采用点。P2 因为主工具已受保护，影响集中在维护尾声。

证据：`agent/AgentLoop.java:229–231,400–402,422–424`；`agent/SessionRuntime.java:302–306,509–525`；`memory/MemoryExtractionService.java:94–129`；`memory/MemoryManager.java:81–108`。SDK 内部线程和默认超时未审计，不把缺少 close 方法直接认定为已发生资源泄漏。

## 包结构评价

五个角色基本合理，不建议把选择、提取和整理合回一个巨型 MemoryService。文件发布能力可提取小的同目录原子发布原语，但语义性策略仍归各服务。多写者所有权统一见 ARCH-013；目前的快照比较不应被误认为文件锁。

Review：**Blocking（ARCH-004 对长期记忆完整性）**；其余两项为有条件风险。没有检查记忆内容的真实性或秘密识别效果，提示词禁止保存秘密不是可证明的内容过滤器。
