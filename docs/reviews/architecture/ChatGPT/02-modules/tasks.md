# 模块审查：持久任务图与工作区所有权

## 当前机制与合理之处

Task 以不可变记录表达 pending → in_progress → completed，构造时检查状态和 owner 是否一致、依赖 ID 是否合法。TaskStore 负责图规则与文件访问，TaskTools 将参数翻译为六项操作，模型不直接决定文件名或 owner。创建用排他新建；更新用同目录临时文件和原子移动；依赖更新检查自环和可达环；认领检查前置任务；完成只返回本次新增的可执行节点，不自动开工。

这个包边界大体合适：工具适配留 tools，领域状态和存储留 tasks。现在不需要任务调度线程、数据库或事件总线。一个存储类同时管图规则和文件 IO 已有拆分收益的可能，但应先围绕故障恢复与单写者约束，不只因方法数量变多就增加仓库接口。

证据前缀 `src/main/java/com/jadecode/`：`tasks/Task.java:31–49`；`tasks/TaskStore.java:65–129,140–231,253–334`；`tools/TaskTools.java:35–51,113–180,185–217`。

## ARCH-012：已认领任务缺少显式释放或失败状态

**P3；可选优化；分类：任务生命周期优化机会。**

执行任务与持久任务本来就是两种身份。运行器执行失败只清理对应命令，不更新持久任务；持久任务 API 只有认领和完成，没有释放、暂停或记录失败。进程结束后记录可能长期处于 in_progress，使用者要自行解释还要做什么。

反向检查：工具固定 owner=agent，同一使用者下次可以读取并继续做，再 complete，并非任务永远无法完成；README 明确不恢复精确断点、不证明完成内容正确。因此这不是缺少自动调度的 Bug，也不应让运行器猜测某项工具调用属于哪条持久任务。

**具体设计**：先增加显式 release 或标记暂停/失败的单项操作，保留 lastOutcome/说明等最少诊断；模型或用户读任务后决定重试，禁止自动把未完成工作标成 completed。若将来需要执行任务关联持久任务，再由 Harness 显式传关联 ID，不能按标题或最近认领推断。先决定状态机，再考虑把图规则从文件存储提成小服务。

收益是跨会话恢复更直白；范围 Task 状态、TaskStore 与工具适配；成本低至中；风险是旧 JSON 兼容、依赖就绪规则和既有 owner 语义。P3 因当前仍可人工恢复，属于长期实用性提升。

证据：`tasks/Task.java:53–56`；`tasks/TaskStore.java:175–231`；`tools/TaskTools.java:23,45–51,165–170`；`agent/SessionRuntime.java:404–417`。未读取实际任务数据，也未判断现有任务是否滞留。

## ARCH-013：工作区单写者是约定，程序没有阻止第二个进程

**P2；有依据的潜在风险；分类：跨进程一致性风险。**

TaskStore 的认领是读图、检查、再原子替换文件，没有跨进程锁；CronScheduler 虽 synchronized，但各 CLI 有独立内存快照，任意提交都可能覆盖另一进程新记录；Memory 的两次快照检查同样不是事务。文件级原子移动只保护单次替换不产生半份文件，不保护“读取后做决定”这段操作互斥。

触发条件是用户在同一工作区启动两个 CLI，或外部程序同时改库。后果可能是重复认领、cron 定义覆盖和记忆整理冲突。README 已说明任务不保证并发互斥、cron 不支持多 CLI 写入，故不把它描述成违反并发支持承诺；但长期本地 CLI 很容易误开两个窗口，静默继续代价较大。

**具体设计**：在宿主会话进入可写模式时取得工作区独占锁，获取失败就明确提示使用者，提供只读查看而非偷偷等待或抢占。将锁所有权集中在工作区宿主，不让每个存储类各锁各的。若未来确有多写者需求，再升级存储事务和版本条件更新，不以 JVM synchronized 冒充跨进程控制。外部手工编辑仍需版本冲突检查，独占 CLI 锁不能控制所有编辑器。

收益是把已声明的支持边界变成可观察约束；范围 Main/CLI、工作区资源生命周期与三个存储；成本中；风险是陈旧锁文件、网络文件系统锁语义和只读模式界定，锁状态应依赖实际 OS 锁而非仅判断文件存在。P2 因需多写者条件，普通单进程流程不受影响。

证据：`tasks/TaskStore.java:175–190,270–284`；`cron/CronScheduler.java:39,171–193,230–252`；`memory/MemoryStore.java:231–233,277–296`；`Main.java:160–165`、`cli/ReplCommand.java:31–35` 无工作区所有权获取。构建与运行被禁止，未启动第二个 CLI 做并发验证。

## 辅助可靠性边界

一个坏任务文件会让 list/snapshot 失败，进而阻止认领和完成；这是偏保守的失败关闭设计，有助于避免基于缺失依赖错误认领。可以以后提供明确的诊断与人工隔离入口，不能悄悄跳过坏依赖来“恢复成功”。目前没有版本字段，但未发生格式迁移，暂不为每个 record 引入通用版本框架。

Review：**Non-blocking**；建议先用单写者边界保护现行文件架构，再评估更复杂存储。
