# 模块审查：后台任务与进程生命周期

## 机制和合理之处

后台管理器将执行中和已完成但未确认的任务都计入 32 项上限。线程启动前先登记，避免秒退命令早于登记；完成结果先进入独立队列，再通知运行器。运行器把结果加进历史，模型合法回复后才删除记录。定时首回复前失败可恢复已取出的通知，不必重跑命令。

必等命令按执行任务 ID 归属，脱离命令才作为后续参考通知。任务失败取消必等命令，退出关闭全部命令，文档没有把“脱离当前任务”说成“退出后继续运行”。每个 shell 使用新进程组，输出由虚拟线程持续排空，避免输出管道堵塞和无限缓冲。run 返回前与 finally 都清理，Running.stop 的幂等标记防止重复杀组。

证据前缀为 `src/main/java/com/jadecode/`：`tools/BackgroundManager.java:96–152,166–231,295–306`；`tools/ShellCommand.java:63–111,115–126,148–174`；`agent/SessionRuntime.java:263–294,322–348,404–415`。

已排除的误判：等待结果不消耗新请求容量；完成结果不是第二份 tool_result；关闭先于后台线程真正启动时，ShellCommand 的 closed 检查仍阻止后续启动。没有证据证明这三条路径存在常见竞态缺陷。

## ARCH-007：同步命令输出被截断却没有告诉模型

**P2；已证实；分类：实际结果完整性缺陷。**

输出读取器保存最多 50,000 个字符并记下 truncated。后台通知会展示截断标记，但同步路径只调用 Result.text()，它只加退出码和正文，没有使用 truncated。模型可能把截断的日志、JSON 或检查结果当作完整输出。后续上下文转存只能保存已经拿到的前缀，不能恢复被 shell 读取器丢弃的尾部。

反向检查：这不是没有输出上限；边读边排空是正确的。后台路径明确说明没有完整输出文件，也是正确的。已有 BashToolTest 反而要求同步返回刚好 50,000 个 x，说明静默截断是现行接口行为，不是本报告假定存在另一个遗漏标记。

**具体设计**：由统一命令结果格式明确表达 exitCode、truncated、保留范围及原文保存位置；即使暂时保留字符串工具结果，也由同一渲染器追加截断说明。若保存完整日志，必须在执行期间流式写入有容量限制的工作区文件，不能等截断后再假装有全量。保留后台“最多 500 字符摘要、无全量文件”的现行语义，除非另行决定改动。

收益是让模型知道证据不完整；范围 ShellCommand 的结果渲染及 BashTool/BackgroundManager；成本低；兼容风险是现有精确字符串测试和输出消费者需要调整。P2 因为资源已受限，主要影响判断可靠性。

证据：`tools/ShellCommand.java:46–52,97–98,115–126`；`tools/BackgroundManager.java:121,138–140,266–274`；`tools/BashTool.java:175–179`；`src/test/java/com/jadecode/tools/BashToolTest.java:57–61`。

## 条件限制与演进

Linux 的 setsid/kill、主动另开 session 的程序、断电与 SIGKILL 的限制已在 README 说明，不作为新缺陷。进程组号和清理命令的实际 OS 行为，以及输出 reader 在所有关闭场景是否及时退出，本轮只能沿代码检查，仍需受控运行验证。暂不建议为了后台机制引入外部队列、跨进程恢复或通用执行调度器。

Review：**Non-blocking**；与 shell 授权相关的 ARCH-002 和父任务预算 ARCH-008 优先级更高。
