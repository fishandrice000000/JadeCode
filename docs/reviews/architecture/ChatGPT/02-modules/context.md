# 模块审查：上下文整理、归档与工具结果

## 机制与合理之处

上下文门面按固定顺序执行：最新结果批次预算、按消息数裁剪、已消费旧结果转存、按总体字符压缩结果，最后才请求摘要。不同策略保持包私有，对外暴露少量生命周期入口，职责划分比一个超大压缩方法清楚。门面中有一些仅为现有测试保留的委托方法，属于维护成本，但目前不值得单独建立接口层。

工具交换切点会向外调整，不拆开调用和结果；旧结果用位置识别而不是假定 ID 全历史唯一。内容替换重建消息和 content，不改原对象。转存与归档先成功写出，再返回替代历史；写失败不假装有可回读文件。可信 marker 检查真实路径及文件形态，随机新建避免同 ID 覆盖。父子共享门面没有共享消息状态，因此不是天然串话。

## ARCH-005：按消息数裁剪不固定当前目标，目标可能离开模型上下文

**P1；已证实（存在确定的裁剪路径）；分类：实际信息保留缺陷。模型是否因此偏离任务待验证。**

运行器把当前用户请求单独存进 task.goal；但正式请求仍只发送压缩后的 messages 和 system。按消息数裁剪只保留最初几条和最近尾部，中段换成归档路径。该层不接收当前目标；后续若字符数够小就直接返回，不生成包含当前目标的摘要。

具体条件：REPL 已有较早任务记录，新任务的原请求不在最初三条；新任务连续产生足够多的短工具交换后，原请求进入中段。snip 删除它，但历史总字符仍低于 50,000，因此 activeRequest 虽然保存在 Java 内存中，却没有被再次发给模型。模型看到旧会话开头、归档标记和最近工具，当前请求中的限制不再明确可见。

反向检查：摘要和超限压缩会重新放入 Current user request；但没有走这两层时不能兜底。默认裁剪仍保留最近约四十多条，不是每到 51 条就必定删除当前目标。归档保留原文，可供主动回读；然而模型未必知道应读哪段，不能以磁盘存在替代请求可见性。已有自动准备测试在自定义很小阈值时甚至明确期待最新请求被归档，说明不是隐藏保护。

可逐步核对的默认阈值例子（静态推演，未执行）：前两项短任务已有 4 条消息；当前请求在下标 4，随后 23 组短工具交换使历史达到 51 条。头部保留 `[0,3)`，尾部从 5 开始，工具对切点不需要调整，中段 `[3,5)` 恰好含当前请求。只要字符仍低于阈值，下一次正式请求就没有该原文。

**具体设计**：把当前任务目标作为执行契约中的固定输入，交给统一请求构造器在每次正式请求中以固定位置呈现；或让裁剪器获得受保护的任务请求位置，裁剪后重建一份明确的当前请求。前者更适合跨轮、Stop 和后台输入，但要避免重复原文造成无谓膨胀。工具交换保护继续独立维护，不能通过简单插入 USER 消息拆开工具对。摘要仍是参考，归档用于恢复详细证据。

收益是让“内存里记住目标”与“模型实际看见目标”一致；范围运行器、请求构造、裁剪/摘要契约；成本中；兼容风险是重复请求、消息顺序和 existing-history API 的语义。P1 因为长任务正常流程即可触发，影响用户约束。

## 其它边界和演进取舍

当前估算的是 messages 的 JSON 字符数，不是模型 tokenizer 的 token，也不含 system 和工具定义；这是粗预算，不能保证总请求必然低于模型窗口。过长用户请求不能凭压缩算法安全缩成等价指令；应在固定目标后由请求预算层明确报告不可容纳，而非无限摘要。这个方向与 ARCH-008 总预算、ARCH-015 记忆预算共同设计，不另制造一套精确 token 平台。

空摘要仍被当作成功的风险统一归 ARCH-003。共享存储目录不会造成父子文件覆盖；缺少会话归属索引主要影响诊断，可在以后需要回查和保留策略时增加显式 session/agent 身份，不要求为了当前审查搬旧文件、重写 marker 或实现事件溯源。快照归档不等于可恢复的持续会话日志。

归档目录目前没有像 Memory/TaskStore 那样保证真实目录仍在工作区内；若工作区运行目录预先被软链接到外部，就可能向外写文件。此项纳入 ARCH-001 的共享路径服务迁移边界，具体是否应允许用户显式外置存储需要产品决定，不把“指向外部”一律说成已发生泄漏。

Review：**Blocking（ARCH-005 的目标保留）**；其余策略的局部拆分和先保存后替换值得保留。本轮未测量实际 token 成本或摘要质量。
