# 模块审查：工具、权限、文件操作与 Hooks

## 当前机制

工具负责描述输入并返回文本；主执行器负责查表、前置 hook、执行及后置 hook。权限分成硬拒和需审批两组，先查硬拒，再决定能否询问。任务来源由 Harness 保存，定时任务即使拿到审批函数也不能申请交互；子代理继承同一身份。这比按线程身份判断可靠。

文件工具使用统一路径解析器，权限再对解析结果分类。glob 从工作区遍历且不主动跟随目录软链接，没有任意扫描根参数；不能因它没进文件路径审批表就认定可以扫描任意目录。Hooks 按注册顺序执行、首个非 null 短路，当前 Main 先检查工具成员再查权限和日志，顺序正确。

证据前缀：`src/main/java/com/jadecode/`。核心位置：`safety/PermissionGate.java:64–83,108–155`；`Main.java:208–217,240–266`；`tools/GlobTool.java:92–118`。跨层隐式契约另见 [ARCH-011](agent-session.md)。

## ARCH-001：软链接目标没有继续解析，权限可能判断错对象

**P1；已证实（静态控制流）；分类：实际安全边界缺陷。未创建链接或执行复现。**

解析器遇到软链接时，读取目标后直接以该目标继续处理原路径剩余段。如果剩余段已经空了，就立即返回；它不会再检查“目标本身是不是另一个软链接”，也不会把目标路径中的祖先目录重新解析。

静态例子：工作区中 `a → b`，而 `b → /etc/hostname`。检查 a 得到工作区内的 b，路径围栏允许；读工具再次解析 a 仍得 b，真正的文件 IO 会继续跟随 b 到最终目标。审批检查和实际 IO 的对象不一致。写入场景同理取决于权限和最终目标是否存在。另一个条件是有软链接目录后接 `..`：解析之前先 normalize 可能改变其文件系统语义，不能把词法简化视为真实规范化。

反向检查：直接指向外部的一层链接、悬空链接、普通 `../` 已有实现和测试；工具执行时确实再次调用相同解析器。重算不能纠正同一算法的遗漏。Memory 和任务库使用的 toRealPath/非链接检查也不能替文件工具兜底。并发替换链接仍是独立的检查/使用时间差，即使修好链接链也需要界定。

**具体设计**：路径解析返回最终待操作目标及分类所需信息。已有路径采用完整真实路径解析；不存在的写目标先规范化最近存在的祖先，再组合未存在部分。若自行逐段解析，必须把链接目标的所有段放回待处理队列、限制链接跳数并拒绝循环与解析失败，不能失败后按原路径继续放行。授权后让文件服务消费同一已授权目标；需要抵御并发敌对改链时，再引入不跟随链接的目录句柄式访问或明确限制。

收益是让文件权限针对实际对象；范围解析器、路径守卫和三个文件工具；成本中；兼容风险是原先被容忍的坏链接或目录别名开始报错。P1，因为静态可构造绕过硬拒的路径，条件明确；没有证据支持升级 P0 或声称已发生泄露。

证据：`safety/PathResolver.java:46–58,72–86`；`safety/PathGuard.java:31–42,51–60`；`tools/ReadFileTool.java:91–97`；`tools/WriteFileTool.java:89–96`；`tools/EditFileTool.java:90–110`。反证检查：`src/test/java/com/jadecode/safety/PathResolverTest.java:44–82` 和 `src/test/java/com/jadecode/safety/PathGuardTest.java:47–74` 仅有单层目标，未覆盖目标再为链接的分支。

## ARCH-002：命令文本规则不足以承担 shell 权限边界

**P1；有依据的潜在风险；分类：安全架构风险。规则有限这一点已证实，危险命令未执行。**

文件工具会做路径审批，但 bash 把任意字符串交给完整 `/bin/sh -c`，权限仅检查几个子串和正则。命令使用相对越界路径、解释器、脚本、间接变量或其它写文件命令时，可以不出现这些关键词；以 `../` 访问工作区外文件也不会自动进入文件工具的路径围栏。定时来源禁止的是“需要询问的操作”，未命中规则的命令仍能执行，不能称为只读或无破坏能力。

反向检查：deny list 和审批确实阻止常见显式写法，setsid 和 kill 管理生命周期；README 也明确“进程组清理不是沙箱”。所以不将“没有容器”本身列为 Bug。问题在于这组启发式规则无法保证 Main 提示词中“所有破坏操作均需审批”的承诺。扩大黑名单只能改善提示，不能使任意 shell 成为可验证的路径边界。

**具体设计**：区分可信个人终端模式和受限自动模式。可信模式明确其审批是辅助防误操作；自动模式按真实能力授权，对任意 shell 采用默认拒绝/显式授权，或放入操作系统限制的工作区运行环境，再对网络、可写挂载和秘密继承单独授权。优先沿现有 ExecutionContext 选择策略，保持父子一致；不把提示词作为权限实现，不以解析全部 shell 作为唯一防线。

收益是让权限承诺与执行能力匹配，尤其保护未来自动化入口；范围任务身份、PermissionGate、shell 启动边界和说明；成本高（若实现 OS 隔离），中（若先收紧自动模式）；兼容风险是定时及既有 bash 工作流需要明确授权。P1 因为普通文本检查无法限制具备真实写权限的进程。

证据：`safety/CommandPolicy.java:13–17,25–71`；`safety/PermissionGate.java:64–83,108–136`；`tools/ShellCommand.java:75–78`；`Main.java:385` 的破坏性操作承诺。已有规则测试 `src/test/java/com/jadecode/safety/CommandPolicyTest.java:12–44` 和 `src/test/java/com/jadecode/safety/PermissionGateTest.java:88–105,132–140` 只证明命中规则后的行为。

## ARCH-006：输出预算晚于读取，不能限制进程内存与扫描成本

**P1；有依据的潜在风险；分类：资源可靠性风险。**

read_file 即使给很小的 limit，仍先读完整文件和全部行再裁剪。glob 先遍历、收集、排序全部匹配，最后才保留 200 条。后面的工具结果转存与上下文预算限制的是发给模型的内容，不是读取期间占用的内存。大生成文件、大单行文本或海量目录可能占满堆、长时间堵住唯一消费者；OutOfMemoryError 也不在普通工具异常闭合路径中。

反向检查：shell 使用边读边截的 50,000 字符缓冲，确实避免了同类无限输出问题；文件工具没有相同的入口限制。Memory/Skill/TaskStore 也有先全读后预算的模式，影响扩展面见 memory 报告，但本项主要由基础 IO 层承担。

**具体设计**：读工具同时设置行数和字节/字符预算，流式扫描到界限就停，并返回明确截断及继续读取位置；不能只限制行数，因为一行也可很大。glob 使用有遍历计数/时长上限的目录访问器，明确提前停止与排序契约；若仍要全局字典序前 200，可用有界集合减少匹配存储，并单独限制访问成本。不要在这一轮引入复杂索引服务。

收益是把模型预算和机器资源预算分开；范围文件工具、扫描辅助服务，必要时记忆/技能加载；成本中；风险是返回格式和完整排序习惯改变。P1 因为单次模型工具参数就能影响整个 CLI 可用性，实际严重程度仍需在受控大文件环境验证。

证据：`tools/ReadFileTool.java:83–108`；`tools/GlobTool.java:92–118`；对照 `tools/ShellCommand.java:115–126`；`agent/AgentLoop.java:340–346` 只捕获 RuntimeException。

## ARCH-017：编辑和覆盖直接截断原文件，没有原子发布

**P1；有依据的潜在风险；分类：文件数据完整性风险。**

edit_file 先读完整旧内容、内存替换，然后直接 writeString 覆盖原路径；write_file 也直接覆盖。写入失败、磁盘满或进程中途退出时，原文件可能已被截断，只剩部分内容。工具随后返回 Error，并不代表原内容仍在。当前 edit_file 也没有确认从读取到写入期间文件版本未变化，后台 shell 或外部编辑器的更改可能被覆盖。

反向检查：持久任务更新和 cron 状态已采用同目录临时文件加原子移动，说明项目已有可借鉴做法；源码编辑未复用。Git 可以帮助人工恢复已跟踪内容，但未提交的新工作不一定可恢复，也不应将 Git 当作写入事务。

**具体设计**：在权限确定后的目标同目录写候选，完成后原子替换；保留必要权限等元数据，失败只清理自己的候选。编辑操作记录读取版本，在发布前检查是否改变并报冲突；不能假装该检查具备跨进程原子隔离。需要更强并发保证时再增加明确的工作区写入协调。先与 ARCH-001 对齐路径，再修改发布方式，避免原子移动改变链接文件语义。

收益是降低任务修代码时损坏用户文件的概率；范围两个写工具及文件操作服务；成本中；风险是文件权限、软链接目标和原子移动兼容性，必须明确失败而非静默退回直接覆盖。P1 因为可能损失用户当前工作，而不是普通输出质量问题。

证据：`tools/EditFileTool.java:93–113`；`tools/WriteFileTool.java:92–96`；对照 `tasks/TaskStore.java:270–284`、`cron/CronScheduler.java:230–252`。本轮未注入磁盘满或中断，具体文件系统行为待验证。

## 辅助代码与输入契约

基础文件工具重复检查“字段是否存在”，再用 asText/asInt 做隐式转换；较新的任务/cron 工具严格检查真实 JSON 类型。非法 glob 表达式、非法路径等还可能以运行异常结束整个任务，而不是返回可让模型修正的输入错误。这是 ARCH-011 执行服务中应统一的输入阶段：先验证，再授权，再执行，区分参数错误、工具执行失败与系统异常。应保留 ToolSchema 的 required 自检、Todo 的候选验证后整体采用，不需要统一为庞大 JSON Schema 框架。

## 结论

审批身份的传递是清楚的，但路径规范化和 shell 能力承诺存在实质缺口。Review：**Blocking（ARCH-001、ARCH-002 对安全边界）**。所有安全例子均为静态推导，未执行危险命令、改链或写源码验证。
