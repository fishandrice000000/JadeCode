# 模块审查：时间规则、待交付与重投

## 当前机制和包职责

cron 包负责规则、定义和待交付文件；agent.CronProducer 负责定时检查及向会话提交；运行器负责首次模型回复确认。这一分工合理：时间规则不调用模型，生产者不修改历史，业务执行不躲进定时线程。CronTools 留 tools 作为模型参数适配也合适，不必因为工具与 cron 有关联就合并包。

每个记录保存是否重复、是否持久、pending 和上次命中的分钟。检查只看当前分钟，不补跑停机时间；pending 合并后续匹配，避免同一项任务积压无限副本。进程内 lease 防止重复入队，队列满恢复 lease；取消会移除 ready 和 lease，真正开始前运行器还会检查记录是否存在。首个正式模型回复前失败退避五秒，连续三次暂停自动投递，但不阻止人工任务。确认不是业务成功，首回复后工具失败也不会重跑整项业务。

源码证据前缀 `src/main/java/com/jadecode/`：`cron/CronScheduler.java:73–168`；`agent/CronProducer.java:81–161`；`agent/SessionRuntime.java:210–215,267–269,404–410`。README 对 live REPL、run 不常驻、至少一次交付以及多进程限制说明基本准确。

## 存储与故障处理

恢复严格检查七字段、真实 JSON 类型、最多 100 项和 16 MB 读取上限；非普通文件及软链接被拒绝。状态更新先序列化、写候选、原子替换，最后采用内存候选；确认发布失败时 lease 仍保留，避免本进程立即重做，重启后仍可能重复。没有外部业务幂等键，所以“任意外部副作用恰好一次”并未实现，文档也没有这样承诺。

证据：`cron/CronScheduler.java:171–209,230–259`；`agent/CronProducer.java:132–139`。单写者约束见 [ARCH-013](tasks.md)，有效回复判定不足见 [ARCH-003](llm-messages.md)。它们是跨模块问题，本报告不重复编号。

## 待确认 Q-CRON-01：星号步进在日/月上的锚点

解析器用 `value % step == 0` 构造星号步进集合。分钟从 0 开始不显差异，但日/月从 1 开始，`*/2` 会选择偶数，`*/40` 在日期域可生成空集合且不报错。规则是否要以字段最小值为步进起点，当前仓库没有明确的输入输出契约。

证据：`cron/CronExpression.java:17–18,60–69`；`cron/CronJob.java:25–34`。这是静态可确认的当前集合算法，不能仅据习惯断言用户要的是另一种定义。本轮将其保留为 **Question / 待验证契约**，不计为已证实缺陷、不人为分配优先级。后续应明确日/月示例、拒绝永不匹配的表达式与否，再决定是否改变语义，避免无提示改变现有定时计划。

## 不建议的重构

不需要引入持久 MQ、独立调度服务或把每次轮询都做成事件线程。若个人需求变成机器关机也能执行，应该明确新增外部宿主能力；不能只把 CronProducer 改成非 daemon 就宣称有守护服务。工作区多写者和模型交付完整性优先于抽象出多套 Scheduler 接口。
