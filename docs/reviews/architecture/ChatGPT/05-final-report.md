# JadeCode 全仓库源码架构审查：最终综合报告

> 2026-10-17 更新：用户要求优先审查架构。最新包边界建议见 [架构优先复审](06-package-boundaries-2026-10-17.md)：agent 仅执行器、会话归 session、CronProducer 归 cron、进程能力归 process。下文保留初版诊断；与新职责方案不同处以复审为准。

## 1. 总体评价

**JadeCode 已有可继续长期演进的结构；主要短板是几个关键边界不够完整，而不是缺少架构框架。** 单消费者拥有父历史、生产者不改历史、模型 SDK 隔离、父子消息隔离、后台启动/完成/采用分开，都是有价值的基础。任务图、记忆和定时库也有各自的职责，不是一份教学脚本简单堆功能。

但当前结构还不能为强权限隔离、完整结果判定和崩溃后数据一致性提供充分保证。最值得优先投入的是：最终文件目标必须与授权一致、模型不完整回复不能假完成、当前目标不能在裁剪中消失、持久化采用必须有明确提交点，以及任务总执行成本必须有上限。

包架构方面，当前按领域分包大体正确；**tools 包的含义已经过宽**。它既包含给模型看的适配器，也包含 OS 进程执行和会话直接依赖的命令管理。共享 ExecutionContext 和 Tool 定义的位置又把多个基础模块绕回 agent。建议调整这两处真实边界，保留 Maven 单模块，不采用外部 MQ、全异步执行、通用 Agent 基类或没有第二种实现需求的接口体系。

Review 总结：**Blocking** 用于路径权限、结果完整性、目标保留与数据发布等长期可靠性边界；**Non-blocking** 用于包迁移和其它渐进优化；**Question** 保留日/月步进契约。这里是架构诊断分级，不是此次实施/验收放行，未修改或修复任何问题。

## 4. 包架构应怎样调整

### 第一处：把进程能力从模型工具包中分离

推荐把 ShellCommand 与 BackgroundManager 放入 `process`。BashTool 留在 tools；它继续解释模型参数、选择同步/后台并渲染回执。会话只向进程服务查询命令事实和取消命令，不接触 Process、kill 或输出 reader。后台管理器不决定 Agent 是否结束，也不持有整个 Agent 上下文；归属标识与等待属性作为明确值传入。

包迁移需要同时处理 ShellCommand/runForeground 的包私有访问和父子不同 shell 生命周期。可以把现有 ShellCommand 整理成公开但很小的同步执行 API，内部 Running 继续私有；也可由一个公开命令服务封装它。当前推荐前者，少引入一层包装。没有第二种执行后端之前，不要求工厂与一套接口/实现一一配对。

### 第二处：把共享契约放到稳定位置

execution 契约包只容纳身份、来源、取消及审批端口；不容纳队列、历史、存储或业务调度。tools、safety、agent 使用这些契约，process 可进一步只使用 owner ID 和取消等必要值。LLM 只接收工具定义，不应依赖可执行 Tool 对象。这样减少的是实际依赖，不只是让目录更漂亮。

### 第三处：复用执行步骤，保留不同宿主

父/子共享回复验证、授权后执行和结果闭合步骤；父仍归会话运行器管理，子仍有独立历史和轮数限制。Context 保留门面与包私有策略；Memory 保留召回/提取/整理分工；Task/Cron 的领域规则不挪入 tools。当前不建立通用万能 Runtime 或强迫所有状态都写成事件日志。

```text
CLI / Main（装配与资源宿主）
  ├─ agent（会话与任务推进） ──> llm / context / memory / process
  ├─ tools（模型适配） ──────> tasks / cron / skills / subagent / process
  └─ safety（授权策略）
       ↑ agent / tools 通过明确的工具执行步骤调用

execution：上述组件共用的小型执行契约
messages + 工具定义：模型协议的值对象
process：依赖 JDK 的进程实现，不反向依赖 Agent 调度或 CLI
```

这是一份目标职责图，不声称现有 import 已符合，也不要求一次性把所有类搬完。部分循环还需通过“定义与执行对象分离”解决，不能只移动一个 Context 类就宣称无环。
